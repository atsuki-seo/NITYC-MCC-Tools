1構文が正しくても成り立たないプログラム

構文解析は、トークン列が文法に従っているかを調べ、従っていれば 抽象構文木(abstract syntax tree, AST) を組み立てる。 抽象構文木では、括弧や区切り記号は節点として残らず、演算子の優先順位は木の形として表される。 しかし、文法に従っていることは、プログラムが意味をなすことを保証しない。次の擬似コードは、どの行も文法の上では正しい。 

1. 変数 n : 整数 ← 真
2. 変数 n : 整数 ← 3
3. もし n ならば
4.   total ← n + 1

1行目は整数型と宣言した変数に真偽値を入れている。2行目は同じ名前を二度宣言している。 3行目は条件に整数を与えている。4行目の total はどこにも宣言されていない。 いずれも「識別子 ← 式」「もし 式 ならば 文」という並び方としては正しいため、構文解析は受理する。 文法が記述するのは語の並び方であり、名前が何を指すか、値がどの型を持つかは文法の外にあるためである。

これらを調べる工程が 意味解析(semantic analysis) である。 入力は構文解析が組み立てた抽象構文木であり、出力は各節点に型を書き込んだ 注釈付き構文木(annotated syntax tree) と、見つかった誤りの一覧である。 誤りが一件でもあれば、後段の最適化・コード生成には進まない。

表 1-1　構文解析を通過するが意味の上で成り立たない誤りと、その検出に要する情報。 名前に関する誤りは宣言の記録を、値に関する誤りは型の規則を参照して初めて判定できる。

誤りの例誤りの種類検出に要する情報
total ← n + 1（total の宣言が無い） 未宣言の名前の使用 宣言の記録（記号表）
同じブロックで n を二度宣言する 重複宣言 宣言の記録とスコープ
変数 n : 整数 ← 真 型の不整合 型規則（宣言の型と値の型の一致）
もし n ならば …（n は整数型） 条件の型の誤り 型規則（条件は真偽値）
引数を一つとる関数 f を f(1, 2) と呼ぶ 引数の個数・型の不一致 宣言の記録と型規則

意味解析の中心は二つの仕組みである。名前をその宣言に結び付ける記号表と、 式や文が型の上で整合しているかを判定する型検査である。 静的型付けの言語では、変数の型が変換時に確定しているため、この型検査を実行前に済ませられる。 動的型付けの言語では同じ検査が実行時に行われる。検査の中身は同じであり、違うのは行う時期である。

  • 型を書かずに済ませるための型推論（制約の生成と単一化）

  • 型推論が制約の生成と単一化によって型を求める仕組みを説明できる
  • 抽象構文木を走査する簡単な型検査器を、記号表と誤りの報告を含めて実装できる
確認問題 1-1

次の誤りのうち、構文解析を通過し、意味解析で初めて誤りとして検出されるものはどれか。

  1. 式 (a + b の閉じ括弧が欠けている
  2. 言語のアルファベットに含まれない文字 @ が式の中に現れる
  3. 宣言されていない変数 count を式の中で参照している
  4. 実行中に変数 d の値が 0 となり、式 x / d が 0 による除算となる
解答

正解: (C)

count を参照する式は、識別子を含む式として文法に従っている。 宣言があるかどうかは語の並び方では決まらず、宣言の記録と照合して初めて判定できるため、意味解析が検出する。

(A) の括弧の対応は語の並び方の規則そのものであり、構文解析が検出する。 (B) の未知の文字はトークンに切り出せないため、字句解析の段階で誤りとなる。 (D) は変換時には値が分からず、実行して初めて判明する。型の上では整数どうしの除算として整合しており、意味解析は通過する。

2記号表とスコープ — 名前を宣言に結び付ける

型検査をするには、式に現れた名前の型が分かっていなければならない。 宣言と使用は抽象構文木の上で任意に離れうるため、宣言を読んだ時点でその内容を記録し、 使用箇所では記録を名前で探す。この記録が 記号表(symbol table) である。

記号表の一行（項目）には、一般に次の情報を記録する。

  • 名前 — 探すときの鍵
  • 種別 — 変数・関数・型名などの区別
  • 型 — 変数であればその型、関数であれば引数の型と戻り値の型
  • 宣言位置 — 誤りを報告するときに「どこで宣言されたか」を示すための行・列

記号表に対する基本操作は、宣言を読んだときに項目を加える登録と、 使用箇所で名前から項目を引く探索の二つである。 探索で項目が見つからなければ、その名前は未宣言である。

スコープ

多くの言語では、ブロックの中で宣言した名前はそのブロックの中でのみ有効である。 名前の宣言が有効な範囲を スコープ(scope) と呼ぶ。 スコープを扱うために、記号表を一枚の表ではなく、スコープごとの表を積み重ねたものとして持つ。

  • ブロックに入るとき、空の表を一枚積む
  • 宣言は、いちばん上（最も内側）の表に登録する
  • 探索は、いちばん上の表から順に下（外側）へ向かって調べ、最初に見つかった項目を採る
  • ブロックを出るとき、いちばん上の表を取り除く。そのブロックで宣言した名前は以後見つからない

名前がどの宣言を指すかがソースコードの入れ子構造だけで定まる方式を 静的スコープ(static scope / lexical scope) と呼ぶ。 多くの言語がこれを採用しており、上の積み重ねた表はこの方式をそのまま実現する。次の擬似コードで動作を確かめる。 

1. 変数 x : 整数 ← 1
2. 変数 y : 整数 ← 2
3. ブロック開始
4.   変数 x : 実数 ← 0.5
5.   x と y を表示する
6. ブロック終了
7. x を表示する

5行目の x は、内側の表で4行目の宣言が先に見つかるため、実数型の変数を指す。 1行目の x は外側の表に残っているが、探索がそこまで届かない。 内側の宣言が外側の同名の宣言を見えなくすることを 覆い隠し(shadowing) と呼ぶ。

表を積み、取り除く流れ

図 2-1 は一時点の記号表である。同じ7行のプログラムを先頭から検査すると、記号表は図 2-2 のように変わっていく。 3行目のブロック開始で表を積み、4行目の宣言をその表に登録する。6行目のブロック終了でその表を取り除くため、 7行目の x の探索は大域の表から始まり、1行目の整数型の変数を指す。

入れ子が深くなっても仕組みは変わらない。ブロックに入るたびに表が一枚増え、探索はいちばん上の表から順に全ての表をたどる。 ブロックを出るときに取り除かれるのは、いちばん上の一枚だけである。

重複宣言の判定

同じ名前を同じスコープで二度宣言するのは誤りであるが、内側のスコープで外側と同じ名前を宣言するのは覆い隠しであり、誤りではない。 二つを分けるのは、登録の際に調べる範囲である。図 2-3 は、宣言を登録しようとする時点の記号表を並べたものである。

誤りやすい点

重複宣言の判定に、探索の手続きをそのまま使ってはならない。探索は全ての表をたどるため、図 2-3 の右でも2行目からのスコープの x を見つけ、 正しい覆い隠しまで誤りとして報告してしまう。 なお、内側での同名の宣言そのものを禁止する言語もあり、この扱いは言語によって異なる。

確認問題 2-1

静的スコープの言語で次の擬似コードを検査する。6行目と8行目に現れる a は、それぞれ何行目の宣言に結び付くか。 

1. 変数 a : 整数 ← 1
2. ブロック開始
3.   変数 b : 整数 ← a + 1
4.   ブロック開始
5.     変数 a : 実数 ← 2.5
6.     a を表示する
7.   ブロック終了
8.   a を表示する
9. ブロック終了
  1. 6行目は5行目、8行目は1行目の宣言に結び付く
  2. 6行目も8行目も1行目の宣言に結び付く
  3. 6行目も8行目も5行目の宣言に結び付く
  4. 5行目が重複宣言の誤りとなり、結び付く宣言は定まらない
解答

正解: (A)

6行目の時点では、4行目で積んだ表に5行目の a が登録されている。探索は内側の表から始まるため、5行目の宣言が見つかる。 7行目でその表が取り除かれるので、8行目の探索は2行目で積んだ表（b のみ）を経て大域の表に達し、1行目の宣言が見つかる。

(B) は探索を外側の表から始めると考えた誤りである。外側から探すと、内側で宣言した名前が常に外側の同名の宣言に負けてしまう。 (C) は、ブロックを出た後も内側の表が残る、あるいは最後に読んだ宣言が有効になると考えた誤りである。表はブロックを出るときに取り除かれる。 (D) は覆い隠しと重複宣言を混同している。重複宣言はいちばん上の表に同名の項目がある場合に限られ、5行目の時点でその表は空である。

3型検査 — 構文木をたどって型規則を当てはめる

型検査(type checking) は、抽象構文木の各節点について型を求め、 言語の定める規則に合っているかを判定する工程である。この規則を 型規則(typing rule) と呼ぶ。 型規則は「子の型が〜であれば、この節点の型は〜である」という前提と結論の形で書ける。 

前提: e1 の型が 整数、かつ e2 の型が 整数
結論: e1 + e2 の型は 整数

前提が満たされなければ、その節点で型の不整合が見つかったことになる。 変数の型は記号表から得る。型規則の文脈では、名前から型への対応を 型環境(type environment) と呼ぶが、実装上は記号表がこれを担う。 本講で用いる小さな言語の型規則を表 3-1 に示す。

表 3-1　本講で用いる言語の型規則。式の規則は節点の型を結論とし、文の規則は文が正しいかを結論とする。 いずれの規則も、子の型だけを見て判定できる。

節点前提結論
整数の定数（3 など）なし整数
真偽値の定数（真, 偽）なし真偽値
変数の参照 x記号表で x の型が TT
e1 + e2（-, *, / も同じ）e1 が整数、e2 が整数整数

子を先に、親を後に

表 3-1 の式の規則は、どれも子の型を前提とする。したがって、ある節点の型を決める前に、その子の型が全て決まっていなければならない。 これを満たすたどり方は、子を全て訪れてから親を処理する 後順走査(post-order traversal) である。 型は葉で決まり、規則を一段ずつ当てはめながら根へ向かって決まっていく。

式 a * (b + c) < d を例にとる。a, b, c, d はいずれも整数型と宣言済みとする。 抽象構文木には括弧の節点は無く、b + c が先に結び付くことは、+ の節点が * の子になっているという木の形で表されている（図 3-1）。

(1)〜(3) の葉は記号表を引いて整数型と決まる。(4) の + は子が二つとも整数であるから、規則により整数となる。 (5) の * も同様に整数、(6) の d は整数、(7) の < は子が整数と整数であるから真偽値となる。 この式を もし … ならば の条件に置けば、条件が真偽値であるという文の規則も満たされる。

前提が破れる節点

文を含み、途中で前提が破れる例として、整数型の n について もし n < 10 ならば n ← n + 真 を検査する（図 3-2）。 条件分岐の節点は、まず条件の部分木を検査し、その型が真偽値であることを確かめてから、本体の文を検査する。 文の節点は型を持たず、表 3-1 の規則を満たすかどうかだけを判定する。

節点の種類ごとに規則が一つ対応するという構造は、再帰下降構文解析で非終端記号ごとに一つの関数を用意したのと同じ考え方である。 型検査器は「節点を受け取り、子を再帰的に検査してから、その節点の種類に応じた規則を当てはめる」手続きとして書ける。

補足: 暗黙の型変換

整数と実数の加算を許す言語では、規則を「一方が実数ならば結果は実数」とし、整数側の子と + の間に 「整数を実数に変換する」節点を挿入することが多い。このように処理系が自動で行う変換を 暗黙の型変換(implicit conversion / coercion) と呼ぶ。 どの組合せで変換を許すかは言語によって大きく異なり、全く許さない言語もある。

確認問題 3-1

x と y を整数型、f を真偽値型と宣言した。式 (x + y) < 2 * f を表 3-1 の規則で後順走査により検査したとき、 型の不整合が最初に見つかる節点はどれか。

  1. * の節点
  2. < の節点
  3. 括弧 ( ) に対応する節点
  4. 不整合は見つからず、式全体の型は真偽値となる
解答

正解: (A)

抽象構文木の根は < であり、左の子が x + y、右の子が 2 * f である。 後順走査では左の部分木を先に検査し、x + y は整数となる。続いて右の部分木で 2 が整数、f が真偽値と決まり、 * の節点で「両方が整数」という前提が満たされないことが分かる。

(B) は検査が根から始まると考えた誤りである。根の規則を当てはめるには子の型が必要であり、子の検査が先に済む。 (C) は括弧が節点として残ると考えた誤りである。抽象構文木では括弧は木の形に吸収され、節点にはならない。 (D) は < の結論が真偽値であることだけを見て、子の検査を省いた誤りである。型規則は前提を満たした場合にのみ結論を与える。

4意味エラーの検出と報告

型検査や記号表の探索で見つかった誤りを 意味エラー(semantic error) と呼ぶ。 誤りを見つけることと同じくらい、それを利用者が直せる形で伝えることが重要である。 報告には一般に次の要素を含める。

  • 位置 — 行と列。字句解析がトークンに付けた位置を、構文解析が抽象構文木の節点へ引き継いでおく
  • 誤りの種類 — 未宣言、重複宣言、型の不整合など
  • 期待したものと実際のもの — 「条件には真偽値が必要だが、整数が与えられた」のように両方を示す
  • 関連する位置 — 重複宣言であれば、先に宣言された位置。記号表の宣言位置がここで使われる

位置が抽象構文木に残っていなければ、意味解析は誤りの存在を知りながら場所を示せない。 節点に位置を持たせることは、構文解析の段階で済ませておく必要がある。

§ 1 の4行のプログラムを検査すると、次の誤り一覧が得られる。各行は「行:列: 種類: 内容」の形式で書かれている。 

1:1: 型の不整合: 整数 の変数 n に 真偽値 の値は入れられない
2:1: 重複宣言: n は既に 1:1 で宣言されている
3:4: 条件の型の誤り: 条件には真偽値が必要だが 整数 が与えられた
4:3: 未宣言: total は宣言されていない

1行目の宣言は型の不整合を含むが、n は整数型として登録される。そのため2行目は重複宣言となり、 3行目の条件 n は整数型と分かって条件の型の誤りとなる。報告に含める要素が一覧のどこに現れているかを表 4-1 に示す。

表 4-1　報告に含める要素と、上の誤り一覧での現れ方。列は、行番号の表示を除いた行頭からの文字の位置である。 関連する位置は全ての誤りにあるわけではなく、重複宣言のように先行する宣言が関わる場合に加える。

要素誤り一覧での現れ方情報の出どころ

最初の誤りで止めない

誤りを一件見つけるたびに処理を打ち切ると、利用者は一件直すごとに変換をやり直すことになる。 そこで型検査器は、誤りを一覧に記録したうえで検査を続け、最後にまとめて報告する。

ただし、そのまま続けると一つの誤りが連鎖して多数の報告を生む。 p を宣言し忘れた x ← p * 2 + 1 では、p の型が決まらないため、 * も + も代入も前提を満たせず、それぞれが誤りを報告してしまう。 利用者にとって意味があるのは最初の一件だけである。

これを防ぐために、型が決まらなかった節点には特別な 誤り型(error type) を与える。 誤り型は「既に報告済みの誤りに由来する」ことを表し、子に誤り型がある節点は、自らは報告せずに誤り型を親へ渡す。

誤り型を受け取った節点は報告しないが、検査そのものは続く。兄弟の部分木に別の独立した誤りがあれば、それは別に報告される。 抑えられるのは同じ原因に由来する報告だけである。 図 4-2 は、p と q がともに宣言されていない場合の x ← p + q である。

確認問題 4-1

p と q がともに宣言されていない状態で、宣言文 変数 r : 整数 ← p * 2 + q を検査する。 誤り型による連鎖の抑制を行う型検査器が報告する誤りは何件か。

  1. 1 件
  2. 2 件
  3. 3 件
  4. 5 件
解答

正解: (B)

p と q はそれぞれ独立に未宣言であり、どちらも記号表の探索で見つからないため、一件ずつ報告される。 * は子の p が誤り型、+ は両方の子が誤り型、宣言文は初期化式が誤り型であるため、いずれも報告しない。

(A) は最初の誤りで検査を打ち切ると考えた誤りである。誤り型は検査を止めるものではなく、同じ原因に由来する報告を抑えるものである。 (C) は、宣言文で「整数型の変数に誤り型の値を入れる」不整合を別に報告すると考えた誤りである。初期化式の誤り型は既に報告済みの誤りに由来する。 (D) は連鎖を抑えない場合の件数（p, q, *, +, 宣言文）である。

5型推論 — 書かれていない型を求める

ここまでの型検査は、全ての変数と引数の型が宣言に書かれていることを前提としていた。 しかし 変数 n : 整数 ← 3 の 整数 は、右辺の 3 から明らかである。 書かれていない型を、型規則に基づいて処理系が求めることを 型推論(type inference) と呼ぶ。 型推論は型検査を省くものではなく、型を求めたうえで型検査を行うものであり、静的型付けの一種である。

変数の初期化式のように、子の型が全て分かっている場合は、後順走査で求めた型をそのまま変数の型とすればよい。 難しいのは、引数のように使われ方からしか型が分からない名前である。次の関数を考える。 

関数 f(a, b) = (a + 1) < b

a と b の型はどこにも書かれていない。a が整数でなければならないことは、a を検査する時点ではなく、親の + を検査する時点で初めて分かる。 そこで型推論は、型検査を次の二段階に分ける。

  1. 制約の生成 — 型の分からない箇所に未知数を置き、各節点の型規則が要求する等式を集める
  2. 制約の解決 — 集めた等式を全て満たす未知数の値を求める

制約の生成

型の未知数を 型変数(type variable) と呼び、α, β, t1 のように書く。 抽象構文木を後順走査し、各節点で型規則の前提と結論を、型どうしの等式として書き出す。 この等式を 型制約(type constraint) と呼ぶ。 検査ではその場で前提の成否を判定していたが、推論では判定を保留して等式として記録する点が異なる。

単一化による制約の解決

集めた等式を一つずつ取り出し、型変数に当てはまる型を決めていく。この手続きを 単一化(unification) と呼ぶ。 決まった「型変数 → 型」の対応の集まりを 置換(substitution) と呼び、等式を取り出すたびに、まずそれまでの置換を当てはめてから次の規則で処理する。

  • 両辺が同じ型（整数 = 整数 など） — 何もしない
  • 一方が型変数（α = 整数 など） — 置換に「α → 整数」を加える
  • 両辺が同じ形の複合型（関数型 (α) → β と (整数) → 真偽値 など） — 対応する部分どうしの等式に分けて処理する。 例えば (α) → β = (整数) → 真偽値 は、引数どうしの α = 整数 と戻り値どうしの β = 真偽値 の2本に分かれる
  • 両辺が異なる型（整数 = 真偽値 など） — 解が存在しない。型の誤りとして報告する

表 5-1　図 5-1 の型制約を順に単一化した経過。等式を取り出すたびにそれまでの置換を当てはめるため、 (4) は (3) で決まった t1 によって「整数 = 整数」となり、何もせずに済む。

二つの分岐の型を等しくする場合のように、両辺がともに型変数の等式 α = β も生じる。 この場合は「α → β」を置換に加える。α の値はまだ決まらないが、β が決まった時点で α もそれに従う。 表 5-2 は、等式 α = β, β = 整数, α = 整数 をこの順に単一化した経過である。

表 5-2　型変数どうしの等式を含む単一化。(3) で α に置換を当てはめると、α はまず β に、β はさらに整数に置き換わる。 置換は一度で終わらせず、型変数が残らなくなるまで繰り返し当てはめる。

等式置換を当てはめた形処理処理後の置換

解が無い場合 — 推論による誤りの検出

条件式を値として持つ次の関数を考える。もし c ならば e1 そうでなければ e2 の型規則は、 「c が真偽値、かつ e1 と e2 が同じ型 T であれば、全体の型は T」とする。 

関数 g(x) = もし x ならば x + 1 そうでなければ 0

x に α を置き、+ の結果に t1、条件式全体に t2 を置いて後順走査する。 条件式の節点は、条件・二つの分岐・全体のそれぞれについて等式を生成する（図 5-2）。

表 5-3　関数 g の型制約の単一化。(4) に置換を当てはめると整数 = 真偽値 となり、解が存在しない（強調）。 誤りは、この等式を生成した条件式の節点の条件 x の位置で報告される。

補足

プログラム全体の制約を集めて単一化する方式は、多くの関数型言語の基礎となっており、 考案者の名から Hindley–Milner 型推論(Hindley–Milner type inference) と呼ばれる。 この方式は、引数の型が使われ方から一つに定まらない関数（受け取った値をそのまま返す関数など）に対して、 「任意の型 α について (α) → α」という型を与えることもできる。

確認問題 5-1

関数 h(x, y) = もし x < y ならば x そうでなければ 0 の型を、表 3-1 の規則と本節の条件式の規則に基づいて推論した。 h の型として正しいものはどれか。

  1. (整数, 整数) → 整数
  2. (整数, 整数) → 真偽値
  3. (α, β) → α（型が書かれていないため、具体的な型は定まらない）
  4. (整数, β) → 整数（y は条件にしか現れないため、任意の型でよい）
解答

正解: (A)

x に α、y に β を置く。x < y の節点から α = 整数, β = 整数 と、条件が真偽値であることが得られる。 条件式の節点からは、二つの分岐 x と 0 が同じ型であること、すなわち α = 整数 が得られ、全体の型も整数となる。

(B) は条件 x < y の型を関数全体の型と取り違えている。条件式全体の型は、条件ではなく分岐の型で決まる。 (C) は型推論の役割を見落としている。型が書かれていなくても、使われ方から生成した制約によって型変数の値が定まる。 (D) は < が右の子にも整数を要求することを見落としている。条件の中に現れる名前にも、その節点の規則による制約が生成される。

確認問題 5-2

ある式から、型制約 α = β, β = 整数, α = 真偽値 がこの順に生成された。これを順に単一化した結果として正しいものはどれか。

  1. 3つ目の等式に置換を当てはめると 整数 = 真偽値 となり、型の誤りとして報告される
  2. α は真偽値、β は整数と決まり、単一化は成功する
  3. 1つ目の等式の時点で失敗する。両辺が型変数の等式は解けないためである
  4. 単一化は成功し、α は整数と真偽値のどちらの値も取りうる型となる
解答

正解: (A)

1つ目で「α → β」、2つ目で「β → 整数」が置換に加わり、α も整数を指すことになる。 3つ目の α = 真偽値 に置換を当てはめると 整数 = 真偽値 となり、両辺が異なる型であるため解が存在しない。

(B) は置換を等式に当てはめずに処理した誤りである。1つ目の等式で α と β は同じ型でなければならないと決まっており、別々の型にはできない。 (C) は型変数どうしの等式を扱えないと考えた誤りである。一方が型変数であれば、もう一方が型変数であっても対応を置換に加えられる。 (D) は単一化の失敗を「複数の型を取りうる」と解釈した誤りである。一つの変数が同時に二つの異なる型を持つことは、型規則の上で許されない。

6型を書くか、推論させるか

型の扱いには、全ての型を書いて検査する方式、一部を推論させる方式、プログラム全体を推論させる方式がある。 さらに、変換時には検査せず実行時に検査する動的型付けも比較の対象となる。 これらは型の整合性を確かめる時期と、利用者が書く情報の量で異なり、同じ型規則の上に成り立つ点で一つの表で比べられる。

表 6-1　型の扱い方の対比。上の方式ほど利用者が書く情報が多く、誤りの報告位置が原因に近い。 記述量の差が効くのは型名が長い場合や入れ子になる場合であり、短い型名ばかりのプログラムでは差は小さい。

推論が報告位置を遠ざける理由

§ 5 の関数 g では、利用者の意図が「x は整数で、条件を書き誤った」なのか「x は真偽値で、x + 1 を書き誤った」なのかは、等式からは決まらない。 単一化は二つの要求が衝突した時点で失敗を報告するため、報告されるのは後から処理された使用箇所であり、誤りを書いた箇所とは限らない。 制約がプログラム全体から集められるほど、衝突する二つの使用箇所は離れうる。

次の例では、正の数かを調べる関数 isPos を n > 0 と書くつもりで、誤って n + 0 と書いている。 この関数は40行目で条件として使われる。戻り値の型を書かない場合、1行目からは「戻り値は整数」という制約が、 40行目からは「条件なので真偽値」という制約が生じ、後から処理される40行目で衝突が報告される。 戻り値の型 → 真偽値 を書けば、1行目の時点で本体 n + 0 が書かれた型と食い違うため、誤りを書いた箇所で報告される（図 6-1）。

この問題が実際に効くのは、推論が関数の境界を越えて広がり、衝突する使用箇所が別の関数にある場合である。 局所的な型推論を採る言語が関数の引数と戻り値には型を書かせるのは、この境界で推論を区切り、誤りの報告位置を書いた箇所の近くに留めるためでもある。 一つの関数の内側で推論が閉じている限り、報告位置のずれは数行にとどまり、記述量を減らす利点が上回る。

検査の結果は後段で使われる

意味解析が節点に書き込んだ型は、誤りの検出に使われるだけではない。後段の処理は、この注釈を前提に動く。

  • 命令の選択 — 同じ + でも、整数どうしなら整数の加算命令、実数どうしなら浮動小数点の加算命令を生成する
  • 記憶域の大きさ — 変数に割り当てる領域の大きさは、その型から決まる
  • 変換の挿入 — 暗黙の型変換を許す言語では、変換の節点を挿入した木がコード生成に渡る
  • 開発環境の支援 — 入力中のプログラムに対して意味解析を繰り返し行い、名前の補完や誤りの表示に用いる

動的型付けの言語では、これらの判断も実行時に値を見て行うことになる。 実行のたびに型を調べる手間が生じるが、それが実行時間を左右するのは、同じ演算を大量に繰り返す処理に限られる。

確認問題 6-1

型注釈を書かずにプログラム全体を推論させる方式では、型の誤りが報告される位置が、実際に誤りを書いた位置から離れることがある。その理由として最も適切なものはどれか。

  1. 矛盾は二つの使用箇所の要求が衝突した時点で判明し、どちらが誤りかは制約からは決まらないため
  2. 型推論は実行時に行われるため、誤った箇所に到達するまで矛盾が判明しないため
  3. 型推論は抽象構文木を根から葉の順にたどるため、葉にある誤りが最後に処理されるため
  4. 単一化は計算量が大きく、処理系が途中で推論を打ち切って残りをまとめて報告するため
解答

正解: (A)

単一化が失敗するのは、同じ型変数に対して異なる型を要求する等式がそろった時点である。 二つの要求のどちらが利用者の意図に反するかは等式には現れないため、処理系は後から処理した側の位置で報告するしかない。

(B) は型推論と動的型付けを混同している。型推論は変換時に行われる静的な検査である。 (C) は走査の順序を誤っている。制約の生成は後順走査で行い、葉から根へ向かう。報告位置がずれる理由は順序ではなく、どちらの使用箇所が誤りかを決められない点にある。 (D) は関係のない要因を原因としている。報告位置のずれは推論を打ち切らなくても生じる、等式の性質に由来するものである。

7型検査器の実装の手引き

ここまでの仕組みを、抽象構文木を走査する型検査器として実装する。型検査器は次の部品からなる。

  • 抽象構文木 — 構文解析器の出力。各節点に種類・子・位置を持ち、型を書き込む欄を用意する
  • 記号表 — スコープごとの表を積み重ねたもの。登録・探索・スコープの開始と終了を提供する
  • 式を検査する手続き — 式の節点を受け取り、その型を返す
  • 文を検査する手続き — 文の節点を受け取り、誤りがあれば一覧に記録する
  • 誤りの一覧 — 位置と内容を記録し、検査の最後にまとめて報告する

1. もし S の先頭の表に 名前 があるならば
2.   先の項目 ← S の先頭の表の 名前 の項目
3.   誤りを記録する(位置, 「名前 は既に 先の項目.位置 で宣言されている」)
4. そうでなければ
5.   S の先頭の表に 名前 → (型, 位置) を加える

手続き 探索(名前)
1. S の表を先頭から順に調べ、名前 があればその項目を返す
2. どの表にも無ければ「無し」を返す

式の検査

式を検査する手続きは、子を先に検査し、その結果に型規則を当てはめる。誤り型の受け渡しもここで行う。 演算子ごとの規則（表 3-1）は、手続きの中に条件として書き並べるより、 「演算子と左右の型の組 → 結果の型」の対応表として持つほうが、規則を追加するときに見通しがよい。 

手続き 式を検査(e)   ※ e の型を返す
1. e の種類で場合を分ける
2.   整数の定数の場合: 結果 ← 整数
3.   真偽値の定数の場合: 結果 ← 真偽値
4.   変数の参照の場合:
5.     項目 ← 探索(e.名前)
6.     もし 項目 が「無し」ならば
7.       誤りを記録する(e.位置, 「e.名前 は宣言されていない」)
8.       結果 ← 誤り型
9.     そうでなければ 結果 ← 項目.型
10.  二項演算の場合:
11.    左 ← 式を検査(e.左)
12.    右 ← 式を検査(e.右)
13.    もし 左 が誤り型 または 右 が誤り型 ならば
14.      結果 ← 誤り型          ※ 報告済みの誤りに由来するので記録しない
15.    そうでなければ
16.      結果 ← 演算規則の表で (e.演算子, 左, 右) を引いた型
17.      もし 該当する規則が無いならば
18.        誤りを記録する(e.位置, 「e.演算子 は 左 と 右 に適用できない」)
19.        結果 ← 誤り型
20. e.型 ← 結果               ※ 注釈付き構文木にする
21. 結果 を返す

16行目で引く演算規則の表は、表 3-1 の式の規則を「演算子と左右の型の組」から「結果の型」への対応として書き直したものである（表 7-3）。

表 7-3　演算規則の表の一部。(+, 整数, 真偽値) のように表に無い組を引いたとき、該当する規則が無いとして型の不整合を記録する。 実数の演算を加えるときは、手続きを書き換えずに行を足せばよい。

演算子左の型右の型結果の型
+整数整数整数
*整数整数整数
<整数整数真偽値
=整数整数真偽値

文の検査

文を検査する手続きは、式の型を求めて文の規則を確かめる。ブロックではスコープを開始・終了する。 

手続き 文を検査(s)
1. s の種類で場合を分ける
2.   宣言の場合:
3.     t ← 式を検査(s.初期化式)
4.     もし t が誤り型でなく、かつ t ≠ s.宣言された型 ならば
5.       誤りを記録する(s.位置, 「s.宣言された型 の変数に t の値は入れられない」)
6.     登録(s.名前, s.宣言された型, s.位置)
7.   代入の場合:
8.     t ← 式を検査(s.右辺)
9.     項目 ← 探索(s.名前)
10.    もし 項目 が「無し」ならば 未宣言の誤りを記録する
11.    そうでなく、t が誤り型でなく、かつ t ≠ 項目.型 ならば 型の不整合を記録する
12.  条件分岐・繰り返しの場合:
13.    c ← 式を検査(s.条件)
14.    もし c が誤り型でなく、かつ c ≠ 真偽値 ならば
15.      誤りを記録する(s.条件.位置, 「条件には真偽値が必要だが c が与えられた」)
16.    子の文をそれぞれ 文を検査 する
17.  ブロックの場合:
18.    スコープ開始()
19.    s の文を先頭から順に 文を検査 する
20.    スコープ終了()

宣言の場合、初期化式に誤りがあっても名前は登録する（6行目は4行目の条件の外にある）。 宣言そのものは書かれており、型も宣言に明記されているためである。 登録しなければ、以後その名前を使う全ての箇所が未宣言として報告され、一つの誤りから多数の報告が生じる。

また、初期化式を検査してから登録している点にも注意を要する。登録を先に行う言語もあり、どちらを採るかは言語の仕様として決める事柄である。 外側に 変数 x : 実数 ← 0.5 がある状態で、内側のブロックの 変数 x : 整数 ← x + 1 を検査すると、 右辺の x が結び付く項目は二つの方式で異なる（表 7-4）。

表 7-4　変数 x : 整数 ← x + 1 の右辺の x が結び付く項目。外側には実数型の x がある。 登録の時期によって、同じ記述が型の不整合にもなり、自分自身の参照にもなる。

方式右辺の x を探索する時点の表（上が内側）結び付く項目検査の結果
初期化式を検査してから登録する 内側: 空 ／ 外側: x : 実数 外側の x（実数） 表 7-3 に (+, 実数, 整数) が無いため、型の不整合となる

誤りは「行:列: 種類: 内容」のような一定の形式で一覧に記録し、検査を終えた後に位置の順に並べて出力する。 形式を固定しておくと、検証のときに期待する出力と機械的に照合できる。§ 4 の誤り一覧と表 4-1 が、この形式の例である。

確認問題 7-1

本節の型検査器（宣言は初期化式を検査してから登録し、誤り型による連鎖の抑制を行う）に次のプログラムを与えた。記録される誤りとして正しいものはどれか。 

1. 変数 n : 整数 ← 10
2. ブロック開始
3.   変数 n : 真偽値 ← 偽
4.   変数 m : 整数 ← n + 1
5. ブロック終了
6. m ← n
  1. 4行目の型の不整合と、6行目の未宣言の 2 件
  2. 3行目の重複宣言と、4行目の型の不整合の 2 件
  3. 誤りは記録されない
  4. 4行目の型の不整合、4行目の宣言の型の不一致、6行目の未宣言の 3 件
解答

正解: (A)

4行目の n は、内側の表にある3行目の真偽値型の宣言を指す。+ は真偽値と整数に適用できないため型の不整合を記録し、誤り型を返す。 4行目の宣言は初期化式が誤り型であるため記録せず、m を内側の表に登録する。 5行目で内側の表が取り除かれるため、6行目では m が見つからず、未宣言を記録する。

(B) は覆い隠しを重複宣言と混同している。3行目の時点で、いちばん上の表（2行目で積んだ表）に n は無い。 (C) は4行目の n が1行目の整数型の宣言を指し、かつ m がブロックを出た後も残ると考えた誤りである。 (D) は連鎖を抑えない場合の結果である。4行目の宣言の不一致は、+ で記録済みの誤りに由来する。

8総括

  • 構文が正しくても成り立たないプログラム — 名前が何を指すか、値がどの型を持つかは文法の外にある。 意味解析は抽象構文木を受け取り、注釈付き構文木と誤りの一覧を出す。
  • 記号表とスコープ — 宣言を登録し、使用箇所で探索する。スコープごとの表を積み重ね、内側から外側へ探すことで静的スコープと覆い隠しを実現する。 重複宣言はいちばん上の表だけで判定する。
  • 型検査 — 型規則は子の型を前提とし、節点の型を結論とする。後順走査で葉から根へ型を決め、前提が満たされない節点で不整合を見つける。
  • 意味エラーの検出と報告 — 位置・種類・期待したものと実際のものを示す。誤り型を親へ渡すことで、一つの原因から報告が連鎖することを防ぐ。
  • 型推論 — 型の分からない箇所に型変数を置いて型制約を集め、単一化で解く。両辺が異なる型の等式が現れれば、型の誤りとして検出される。
  • 型を書くか、推論させるか — 推論の範囲が広いほど記述は減るが、誤りの報告位置が原因から離れうる。 関数の境界で型を書かせる方式は、その中間をとる。意味解析が書き込んだ型は、命令の選択や記憶域の大きさの決定に使われる。
  • 型検査器の実装 — 節点の種類ごとに規則を一つずつ実装し、記号表と誤りの一覧を組み合わせる。誤りの種類ごとに一つずつ入力を用意して検証する。

1構文解析器が解く問題

構文解析(syntax analysis, parsing) は、字句解析器が出力したトークン列を受け取り、 それが文法に適合するかを調べて、適合すれば構文木を、適合しなければ誤りの位置を出力する工程である。 構文解析を行うプログラムを 構文解析器(parser)、あるいはパーサーと呼ぶ。 構文解析器が読む単位は文字ではなくトークンである。本資料では、構文解析器から見たトークンを 字句 と呼ぶ。

文法の振り返り

文法は BNF で記述する。用いる用語は次のとおりである。

  • 終端記号(terminal symbol) — 字句そのもの。"+" のように引用符で囲むか、数 のように字句の種別名で書く
  • 非終端記号(nonterminal symbol) — 字句の並びの種類を表す名前。<expr> のように山括弧で囲む
  • 生成規則(production rule) — 左辺の非終端記号を、右辺の記号列に書き換えてよいという規則。| は右辺の選択肢を区切る
  • 開始記号(start symbol) — 書き換えを始める非終端記号

本資料では、加算・乗算・括弧からなる式の文法を全編で用いる。以下ではこれを文法 G と呼ぶ。開始記号は <expr> である。 

<expr>   ::= <expr> "+" <term> | <term>
<term>   ::= <term> "*" <factor> | <factor>
<factor> ::= "(" <expr> ")" | 数

文法 G は、* を + より強く結び付け、同じ演算子が並べば左から順に結び付けるように書かれている。 図 1-1 は、字句列 1 + 2 * 3 に対する構文木である。2 * 3 が一つの <term> にまとまってから 1 に加えられる形になっており、乗算が先に行われることが木の形に表れている。

二つの向き

構文解析器が求めるのは、この木である。ただし構文解析器が知っているのは、文法と、木の葉に並ぶ字句列だけである。 根は開始記号であることが分かっているので、木を組む向きは次の二通りがある。

  • トップダウン構文解析(top-down parsing) — 根の開始記号から出発し、生成規則で非終端記号を右辺に展開していき、字句列に行き着く
  • ボトムアップ構文解析(bottom-up parsing) — 葉の字句列から出発し、生成規則の右辺に一致する並びを左辺の非終端記号にまとめていき、開始記号に行き着く

どちらの向きでも、各段階で「どの規則を使うか」を決めなければならない。 規則の選び方を誤れば、字句列に行き着かない、あるいは開始記号にまとまらない。 あらゆる選び方を試せば木は見つかるが、その組合せは字句列が長くなるにつれて爆発的に増える。 構文解析の手法とは、字句を左から一つずつ読みながら、規則の選び方を手戻りなく決める方法である。

入れ子の深さだけ記憶が要る

((((1)))) のように、括弧はいくらでも深く入れ子にできる。 閉じ括弧が現れたとき、それがどの開き括弧に対応し、外側にまだいくつの括弧が開いているかを覚えておかなければならない。 覚えておく量は入れ子の深さに比例し、上限がない。 有限個の状態しか持たない有限オートマトンでこれを判定できないのはこのためであり、字句の切り出しと、字句の並び方の検査が別の工程に分かれている理由でもある。

構文解析器は、この記憶を次のいずれかの形で持つ。 トップダウンの再帰下降法では、関数の呼び出しの積み重なりが記憶になる。 ボトムアップのシフト還元法では、明示的なスタックが記憶になる。

本講の到達点
  • トップダウン構文解析とボトムアップ構文解析の違いを、構文木を組む向きとして説明できる
  • 文法から再帰下降パーサーを設計でき、左再帰の除去と、FIRST・FOLLOW 集合による選択肢の判定ができる
  • シフト還元法の動作を追跡し、LR 構文解析がシフトと還元を選び分ける仕組みを説明できる
  • 文法と要件に応じて手法を選び、AST を構築しエラーを報告する再帰下降パーサーを実装できる
確認問題 1-1

構文解析器が、深さに上限のない括弧の入れ子を正しく扱うために必要とするものとして、最も適切なものはどれか。

  1. 入れ子の深さに応じて増やせる記憶。再帰呼び出しの積み重なりやスタックがこれにあたる
  2. ソースコードを一文字ずつ読み、括弧の文字を直接数える仕組み
  3. 想定される最も深い入れ子に対応できるだけの、十分に多い有限個の状態
  4. 括弧を含む字句の種別を正規表現で定め、字句解析の段階で対応を確かめる仕組み
解答

正解: (A)

開いたままの括弧を覚えておく量は入れ子の深さに比例し、上限がない。 そのため、必要に応じて伸ばせる記憶が要る。再帰下降法では関数呼び出しの積み重なり、シフト還元法ではスタックがこれを担う。

(B) は、構文解析器の入力を取り違えている。構文解析器が受け取るのは字句解析器の出力した字句列であり、文字ではない。 (C) は、状態を増やせば足りると考えた誤りである。状態数をどれだけ多く定めても有限である限り、それより一つ深い入れ子を判定できない。 (D) は、字句解析の役割を取り違えている。正規表現と有限オートマトンで扱える言語は括弧の対応を判定できないため、この検査は構文解析が担う。

2再帰下降法 — 非終端記号を関数にする

トップダウン構文解析を手で書く代表的な方法が 再帰下降法(recursive descent parsing) である。 非終端記号一つにつき関数を一つ用意し、生成規則の右辺を、その関数の手順として写し取る。 右辺に非終端記号が現れればその関数を呼び、終端記号が現れれば次の字句がそれであることを確かめて読み進める。 規則が自分自身や他の非終端記号を含むので、関数は互いに、あるいは自分自身を再帰的に呼び出す。手法の名はここから来ている。

関数は、字句列と、次に読む位置を共有する。字句を扱う基本の操作として、次の三つを用意する。

  • 次の字句() — 次に読む位置の字句を返す。位置は進めない。このように、読み進めずに先の字句を覗くことを 先読み(lookahead) と呼ぶ
  • 読み進める() — 位置を一つ進める
  • 期待する(x) — 次の字句が x であれば読み進め、そうでなければ構文エラーとする

先読みで選択肢を決める

次の字句を見て選択肢を一つに決め、決めた選択肢を最後まで実行する構文解析を 予測型構文解析(predictive parsing) と呼ぶ。 一方、ある選択肢を試して失敗したら位置を戻して別の選択肢を試す方法を バックトラック(backtracking) と呼ぶ。 バックトラックはどのような文法でも書けるが、選択肢が入れ子になると試す組合せが掛け算で増え、入力が長いと実用的な時間で終わらない。 また、失敗した位置がどこであったかが曖昧になり、誤りの報告が難しくなる。 文法を、次の字句一つで選択肢が決まる形に整えておけば、バックトラックは要らない。

確認問題 2-1

次の生成規則を再帰下降法で関数 文() にする。文() の手順として最も適切なものはどれか。 

<stmt> ::= "print" <expr> | "if" <expr> "then" <stmt>
  1. 次の字句が "print" ならば読み進めて 式() を呼ぶ。"if" ならば読み進めて 式() を呼び、期待する("then") の後に 文() を呼ぶ。どちらでもなければ構文エラーとする
  2. まず 式() を呼び、その後で次の字句が "print" か "if" かを調べて分岐する
  3. 次の字句が "print" ならば読み進めて 式() を呼ぶ。"if" ならば読み進めて 式() を呼び、then() を呼んでから 文() を呼ぶ
  4. "print" の選択肢を最後まで実行し、構文エラーになったら位置を元に戻して "if" の選択肢を実行する
解答

正解: (A)

二つの選択肢は先頭の終端記号 "print" と "if" で区別できるため、次の字句を見て分岐する。 分岐した後は右辺を左から写し取り、非終端記号は関数呼び出し、終端記号は 期待する() とする。 "if" の選択肢の最後で 文() を呼ぶのは、規則の右辺が <stmt> を含むためであり、これが再帰呼び出しになる。

(B) は、右辺の記号の順序を無視している。どちらの選択肢も先頭は終端記号であり、式() から始まる選択肢はない。 (C) は、終端記号と非終端記号を混同している。"then" は字句そのものであり、関数ではなく 期待する("then") で照合する。 (D) はバックトラックである。この規則は次の字句一つで選択肢が決まるため、試して戻す必要がない。戻す処理は時間を要するうえ、誤りの位置の報告も難しくする。

3左再帰と繰り返しへの書き換え

文法 G の <expr> を、表 2-1 のとおりにそのまま関数にすると次のようになる。 

手続き 式()　　— <expr> ::= <expr> "+" <term> をそのまま写したもの
1. 式()
2. 期待する("+")
3. 項()

式() は、最初の手順で字句を一つも読まないまま 式() を呼ぶ。 呼ばれた側も同じ位置から同じ手順を始めるため、再び字句を読まずに 式() を呼ぶ。 位置が進まないので、呼び出しは止まらず、やがて呼び出しの積み重なりのための記憶を使い果たして異常終了する。

このように、生成規則の右辺の先頭に左辺と同じ非終端記号が現れることを 左再帰(left recursion) と呼ぶ。 文法 G の <expr> と <term> はどちらも左再帰を含む。 左再帰を含む規則は、そのままでは再帰下降法で扱えない。 左再帰は、左から順に結び付く演算子を素直に表す書き方であるため、文法を書けば自然に現れる。

左再帰の除去

<expr> ::= <expr> "+" <term> | <term> が生成する字句の並びは、 <term> で始まり、その後に "+" <term> が 0 回以上続くものである。 この観察から、同じ並びを生成する別の規則に書き換えられる。 この書き換えを 左再帰の除去(left recursion elimination) と呼ぶ。 書き換え方は二通りある。

一つは、残りの部分を表す新しい非終端記号を導入する方法である。ε は何も並べないことを表す。 

<expr>  ::= <term> <expr'>
<expr'> ::= "+" <term> <expr'> | ε
<term>  ::= <factor> <term'>
<term'> ::= "*" <factor> <term'> | ε
<factor> ::= "(" <expr> ")" | 数

もう一つは、0 回以上の繰り返しを表す記法 { } を用いる方法である。 BNF に繰り返しや省略可能を表す記法を加えたものを EBNF(extended BNF) と呼ぶ。 

<expr>   ::= <term> { "+" <term> }
<term>   ::= <factor> { "*" <factor> }
<factor> ::= "(" <expr> ")" | 数

繰り返しは、関数の中ではループになる。次の字句が "+" である限り、読み進めて 項() を呼ぶことを繰り返す。 式() は自分自身を先頭で呼ばなくなり、ループを一周するごとに字句を少なくとも一つ読むため、必ず終わる。 

手続き 式()　　— <expr> ::= <term> { "+" <term> }
1. 項()
2. 次の字句() が "+" である間、次の 3〜4 を繰り返す
3.   読み進める()
4.   項()

結合の向きを保つ

左再帰の除去は、生成される字句の並びを変えないが、構文木の形は変える。 この違いは、減算のように結合の向きで結果が変わる演算子で問題になる。 文法に減算を加え、8 - 3 - 2 を考える。 数学の慣習どおり (8 - 3) - 2 = 3 と解釈するには、左の二つを先に結び付ける木を作らなければならない。 このような結び付き方を 左結合(left associative)、その逆を 右結合(right associative) と呼ぶ。

<expr'> を導入する書き換えでは、<expr'> の部分木が右へ右へと伸びる。 この構文木をそのまま演算の木にすると右結合になり、8 - 3 - 2 が 7 と計算される。 左結合の木を得るには、それまでに組んだ左側の木を <expr'> の関数に引数として渡していく工夫が要る。

繰り返しの書き方であれば、この工夫は自然に入る。 ループに入る前に左側の木を持ち、一周するごとに「それまでの木」と「新たに読んだ項」を演算子で結んだ木に置き換えれば、木は左へ伸び、左結合になる。 再帰下降パーサーを手で書く場合は、左再帰を繰り返しに書き換えるのが扱いやすい。

誤りやすい点

左再帰を除くつもりで <expr> ::= <term> "-" <expr> | <term> のように右辺の順序を入れ替えると、無限再帰は起きなくなり、受理する字句の並びも変わらない。 しかし、この規則が作る木は右結合であり、減算の意味が変わる。無限再帰が止まったことと、正しい木が得られることは別の事柄である。

確認問題 3-1

数をコンマで区切って並べた列を表す次の規則がある。生成する字句の並びを変えずに左再帰を除いた規則として、正しいものはどれか。 

<list> ::= <list> "," 数 | 数
  1. <list> ::= 数 { "," 数 }
  2. <list> ::= <list> { "," 数 }
  3. <list> ::= { 数 "," }
  4. <list> ::= 数 | "," <list>
解答

正解: (A)

元の規則が生成するのは、数 で始まり、その後に "," 数 が 0 回以上続く並びである（1, 1 , 2, 1 , 2 , 3, …）。 これを繰り返しで書いたものが (A) であり、右辺の先頭は終端記号 数 なので左再帰はない。

(B) は、右辺の先頭がまだ <list> であり、左再帰が残っている。関数にすれば先頭で自分自身を呼んで止まらない。 (C) は、生成する並びが変わっている。何も並べない場合を含み、末尾が必ずコンマで終わる。 (D) も生成する並びが変わっている。, , 1 のようにコンマで始まる並びを生成し、1 , 2 を生成できない。

41 字句で選べる条件 — FIRST と FOLLOW

予測型構文解析が成り立つには、どの非終端記号についても、次の字句一つを見れば使う選択肢が一つに決まらなければならない。 この条件を確かめるために、次の二つの集合を用いる。

  • FIRST 集合(FIRST set) — 記号列 α から導出される字句の並びの、先頭に来うる字句の集合。FIRST(α) と書く。α が何も並べない ε を導出しうるときは、ε も含める
  • FOLLOW 集合(FOLLOW set) — 非終端記号 A の直後に来うる字句の集合。FOLLOW(A) と書く。入力の終わりを表す $ も含めうる

選択肢 A ::= α | β のうちどちらを使うかは、次の字句がどちらの FIRST 集合に属するかで決まる。 FIRST(α) と FIRST(β) に共通の字句があれば、その字句が来たときに選べない。

選択肢が ε を導出しうる場合は、それだけでは足りない。 <expr'> ::= "+" <term> <expr'> | ε で次の字句が ")" であれば、ε を選んで何も読まずに戻る。 ε を選んでよいのは、次の字句が <expr'> の直後に来うる字句、すなわち FOLLOW(<expr'>) に属するときである。 したがって、FOLLOW 集合が他の選択肢の FIRST 集合と重なっても選べなくなる。

以上の二つの重なりがどこにもない文法を LL(1) 文法(LL(1) grammar) と呼ぶ。 名前は、入力を左から読み（Left to right）、最左導出を作り（Leftmost derivation）、先読みを 1 字句とすることに由来する。 LL(1) 文法であれば、再帰下降パーサーはバックトラックせずに動く。

文法 G を書き換えたものの FIRST と FOLLOW

<expr'> と <term'> を導入して左再帰を除いた文法 G について、FIRST と FOLLOW を求めると表 4-1 のようになる。 FIRST は右辺の先頭を、FOLLOW は右辺の中でその非終端記号の後ろに何があるかをたどって求める。 たとえば <factor> ::= "(" <expr> ")" に <expr> の直後の ")" が現れるので、")" は FOLLOW(<expr>) に属する。 開始記号の後には入力の終わりが来るので、$ も属する。

表 4-1　左再帰を除いた文法 G の FIRST 集合と FOLLOW 集合。ε を選択肢にもつ <expr'> と <term'> では、もう一方の選択肢の FIRST と自身の FOLLOW が重ならないため、1 字句で選択肢が決まる。

非終端記号FIRSTFOLLOW
<expr>(, 数), $

<term>(, 数+, ), $

<expr'> では、次の字句が + なら一つ目の選択肢、) か $ なら ε を選ぶ。 それ以外の字句、たとえば 数 が来れば、どちらも選べないので構文エラーである。 繰り返しの書き方では、この判断がループの継続条件として現れる。次の字句が "+" でなければループを抜けるが、抜けた後に来るべき字句は FOLLOW 集合の要素に限られる。

左再帰を含む規則は、決して LL(1) にならない。 <expr> ::= <expr> "+" <term> | <term> では、一つ目の選択肢の FIRST が <expr> の FIRST そのものであり、二つ目の選択肢の FIRST を必ず含むためである。

重なりを除く — 左くくり出し

左再帰がなくても、選択肢の先頭が共通であれば FIRST 集合が重なる。代入文と関数呼び出しの文がどちらも識別子で始まる場合がその例である。 

<stmt> ::= 識別子 "=" <expr> | 識別子 "(" <expr> ")"

共通の先頭部分を外に出し、その後ろで分岐させれば、重なりは消える。 この書き換えを 左くくり出し(left factoring) と呼ぶ。 

<stmt>      ::= 識別子 <stmt-rest>
<stmt-rest> ::= "=" <expr> | "(" <expr> ")"
確認問題 4-1

次の規則について、LL(1) であるかどうかの判定とその根拠の組合せとして、正しいものはどれか。 

<stmt> ::= 識別子 "=" <expr> | "print" <expr> | 識別子 "(" <expr> ")"
  1. LL(1) ではない。一つ目と三つ目の選択肢の FIRST 集合がともに 識別子 を含み、重なるため
  2. LL(1) ではない。二つ目と三つ目の選択肢がどちらも <expr> を含み、FIRST 集合が重なるため
  3. LL(1) である。三つの選択肢は、先頭から二つ目までの字句を見れば必ず区別できるため
  4. LL(1) ではない。FOLLOW(<stmt>) が、いずれかの選択肢の FIRST 集合と重なるため
解答

正解: (A)

FIRST は選択肢の先頭に来うる字句の集合である。一つ目と三つ目はどちらも先頭が 識別子 であり、次の字句が識別子のときにどちらを選ぶか決まらない。 識別子を外にくくり出せば、LL(1) に書き換えられる。

(B) は、選択肢に含まれる記号と、先頭に来る記号を混同している。<expr> は二つ目と三つ目のどちらでも先頭にはなく、FIRST には関わらない。 (C) は、2 字句の先読みで区別できることを根拠にしている。LL(1) は 1 字句の先読みで決まることを求めるため、2 字句を要するこの規則は LL(1) ではない。 (D) は、FOLLOW を確かめる必要のない場面に持ち出している。FOLLOW が問題になるのは ε を導出しうる選択肢がある場合であり、この規則にはない。

6ボトムアップ構文解析 — シフトと還元

ボトムアップ構文解析の基本となる方法が シフト還元構文解析(shift-reduce parsing) である。 字句を左から読んでスタックに積み、スタックの頂上付近が生成規則の右辺に一致したら、それを左辺の非終端記号に置き換える。 構文解析器が行う操作は次の四つである。

  • シフト(shift) — 次の字句を読み進め、スタックに積む
  • 還元(reduce) — スタックの頂上にある、ある規則の右辺に一致する記号の並びを取り除き、その規則の左辺の非終端記号を積む
  • 受理(accept) — スタックに開始記号だけが残り、入力を読み終えていれば、解析を成功として終える
  • エラー — シフトも還元もできなければ、構文エラーとする

還元で取り除かれる、頂上の記号の並びを ハンドル(handle) と呼ぶ。 還元は、構文木の節を一つ作ることにあたる。取り除いた記号が子、積んだ左辺が親になる。

同じ入力での動作

文法 G を、左再帰を残したまま用いて 1 + 2 * 3 を解析すると、表 6-1 のようになる。 スタックの底には、底を示す記号 $ を置く。表では、字句 数 を値とともに書いた。

還元の順を逆からたどると、開始記号から出発して、毎回いちばん右の非終端記号を書き換える導出になる。 このような導出を 最右導出(rightmost derivation) と呼ぶ。 シフト還元構文解析は、最右導出を逆の順に再現する。

左再帰をそのまま扱える理由

表 6-1 では、左再帰を含む文法 G を書き換えずに用いた。 規則 <expr> ::= <expr> "+" <term> による還元は、<expr>, +, <term> の三つが既にスタックに積まれていなければ起こらない。 積まれるまでに必ず字句を読んでいるため、同じ位置で同じ操作を繰り返すことがない。 再帰下降法では先頭で自分を呼ぶことが無限再帰を招いたが、シフト還元法では、右辺を読み終えてから左辺にまとめるため、この問題が生じない。

  1. 3 回

  3. 5 回
  4. 6 回
解答

(A) は、シフトの回数と取り違えている。字句は 3 個であり、シフトは 3 回である。 (B) は、最後の <expr> ::= <term> を数え落としている。スタックに <term> が残った状態では、開始記号に達していないため受理できない。 (D) は、受理を還元の一つとして数えたか、* を積む前にも <expr> へ還元すると考えた誤りである。後者では <expr> * という並びができ、解析は行き詰まる。

7LR 構文解析 — シフトと還元を選び分ける

表 6-1 の手順 9 と手順 13 は、スタックの中身がどちらも $ <expr> + <term> である。 それにもかかわらず、手順 9 ではシフトし、手順 13 では還元した。違いは次の字句にある。 手順 9 の次の字句は *、手順 13 では $ である。 シフト還元構文解析を手戻りなく進めるには、スタックの中身と次の字句の組から、操作を一つに決める規則が要る。

この規則を表として持ち、それを引いて操作を決める方法を LR 構文解析(LR parsing) と呼ぶ。 名前は、入力を左から読み（Left to right）、最右導出（Rightmost derivation）を逆順に作ることに由来する。

スタックの中身を状態に要約する

スタックの中身はいくらでも長くなりうるため、そのままでは表を引けない。 しかし操作を決めるのに必要なのは、スタックの中身全体ではなく、「どの規則の右辺を、どこまで読み終えたか」である。 規則の右辺に、読み終えた位置を示す印 ・ を入れたものを 項(item) と呼ぶ。 たとえば <term> ::= <term> ・ "*" <factor> は、<term> まで読み終え、次に "*" を待っていることを表す。

規則の数は有限なので、項の数も有限であり、項の組合せとして表される状態も有限個である。 LR 構文解析器は、スタックに記号を積むたびに、この有限個の状態の間を遷移する有限オートマトンを動かし、現在の状態を求める。 そして 現在の状態と次の字句の組で表を引き、シフト・還元・受理・エラーのいずれかを決める。 有限オートマトンにスタックを組み合わせた機械を プッシュダウンオートマトン(pushdown automaton) と呼ぶ。 有限オートマトン単独では扱えなかった入れ子の構造を、スタックを持つことで扱えるようになる。

LR の種類 — 先読みの使い方の違い

図 7-1 の状態では、項だけを見るとシフトと還元のどちらもありうる。 これを次の字句でどう決めるかによって、LR 構文解析はいくつかの種類に分かれる。

表 7-1　LR 構文解析の種類。上から順に、還元の判断に使う情報が精密になり、扱える文法が広がる。LALR(1) は扱える文法の広さと表の大きさの釣り合いがよく、パーサー生成系で広く用いられる。

競合 — 表が一つに決まらないとき

表のある欄に、シフトと還元の両方、あるいは異なる二つの規則による還元が入ってしまうことがある。 前者を シフト還元競合(shift-reduce conflict)、後者を 還元還元競合(reduce-reduce conflict) と呼ぶ。 競合があれば、その文法は表の作り方に対応する種類の LR 文法ではない。 特に、あいまいな文法では、同じ字句列に二通りの構文木があるため、どの種類の表を作っても必ず競合が生じる。 パーサー生成系は競合を報告するので、文法のあいまいさを見つける道具にもなる。

確認問題 7-1

文法 G で字句列 ( 1 + 2 ) を解析している途中で、スタックが $ ( <expr> + <term>、次の字句が ) になった。 次に行う操作として正しいものはどれか。

  1. 規則 <expr> ::= <expr> "+" <term> で還元する
  2. ) をシフトする
  3. 規則 <expr> ::= <term> で還元する
  4. シフトも還元もできないため、構文エラーとする
解答

正解: (A)

この状態は図 7-1 と同じく、右辺を読み終えた項 <expr> ::= <expr> "+" <term> ・ と、* を待つ項を含む。 次の字句 ) は * ではなく、FOLLOW(<expr>) に属するため還元する。 還元すると $ ( <expr> となり、続けて ) をシフトし、"(" <expr> ")" を <factor> に還元できる。

(B) は、還元を後回しにしても構わないと考えた誤りである。シフトすると <term> ) という並びになり、<term> の直後に ) が来る規則の右辺には一致しないため、その先で 1 + 2 を一つの <expr> にまとめられなくなる。 (C) は、ハンドルを頂上の一記号だけと見た誤りである。<term> を <expr> にすると <expr> + <expr> となり、これに一致する規則がない。 (D) は、括弧の中では ) が来うることを見落としている。FOLLOW(<expr>) は ) を含む。

確認問題 7-2

あいまいな文法 <e> ::= <e> "+" <e> | 数 で 1 + 2 + 3 を解析している。 スタックが $ <e> + <e>、次の字句が + のときの状況として、正しいものはどれか。

  1. 還元すれば (1 + 2) + 3、シフトすれば 1 + (2 + 3) の木になり、どちらも続行できるためシフト還元競合となる
  2. 右辺に一致する並びが頂上にあるので、必ず還元する。シフトすれば解析は行き詰まる
  3. 二通りの還元の仕方があるため、還元還元競合となる
  4. 次の字句を 2 字句先まで見れば、操作は一つに決まる
解答

正解: (A)

ここで還元すれば 1 + 2 が先にまとまる。シフトすれば 2 + 3 が先にまとまり、その後で 1 と結ばれる。 どちらの道も開始記号に至るため、表の同じ欄にシフトと還元の両方が入る。これがシフト還元競合であり、字句列に二通りの構文木があることの表れである。

(B) は、表 6-1 の手順 9 で見たとおり、右辺に一致しても還元すべきとは限らないことを見落としている。この文法ではシフトしても行き詰まらない。 (C) は、競合の種類を取り違えている。頂上で還元に使える規則は <e> ::= <e> "+" <e> の一つだけであり、競合しているのはシフトと還元である。 (D) は、先読みを増やせば解決すると考えた誤りである。あいまいさは文法そのものの性質であり、何字句先を見ても二通りの木のどちらかには決まらない。文法を書き換えるか、パーサー生成系で演算子の優先順位と結合の向きを指定して解消する。

8トップダウンとボトムアップの使い分け

ここまでに扱った二つの手法を振り返る。トップダウン構文解析は、再帰下降法として非終端記号ごとの関数で書き、LL(1) 文法であれば 1 字句の先読みで選択肢を決める。 ボトムアップ構文解析は、シフト還元法として字句をスタックに積み、LR の表でシフトと還元を選び分ける。 どちらも字句を左から一度読むだけで構文木を組み、入力の長さに比例する時間で動く。 したがって、処理速度は手法を選ぶ根拠にならない。違いは、扱える文法と、構文解析器の作り方にある。

誤りの報告どの関数で何を期待していたかが分かるため、「) が必要」のように具体的に書きやすい状態番号と次の字句しか手掛かりがなく、分かりやすい文面にするには追加の手当てを要する
文法の変更関数を書き直す。変更のたびに左再帰や FIRST の重なりが生じていないかを人が確かめる文法を書き直して生成し直す。問題があれば競合として機械的に報告される
1 + 2 * 3 での動き呼び出しが根から葉へ広がり、戻りながら木がまとまる（表 5-1）シフト 5 回、還元 8 回で、葉から根へ節を作る（表 6-1）

扱える文法の広さが効くのは、既存の言語の文法を、規格どおりの形でそのまま受け入れなければならない場合である。 文法を自分で設計できるなら、はじめから LL(1) になるよう決めればよく、この差は問題にならない。 一方、誤りの報告のしやすさは、文法の形に関係なく、利用者が触れる構文解析器であれば常に効く。

実務での位置づけ

パーサー生成系は、文法を書くだけで構文解析器が得られ、文法のあいまいさを競合として検出できるため、言語の設計段階や、文法を頻繁に変える小さな言語で有効である。 一方、広く使われる言語の処理系では、手で書いた再帰下降パーサーを採用する例が多い。 利用者に分かりやすい誤りの報告を出せること、誤りの後も解析を続けて複数の誤りを報告する工夫を組み込みやすいこと、文脈に応じた例外的な規則を書き足しやすいことが理由である。

補足

再帰下降法で優先順位の段階が多い式を扱うと、段階ごとに関数が一つずつ増え、呼び出しが深くなる。 このため、式の部分だけを、演算子ごとに優先順位と結合の向きを表にして解析する方法と組み合わせる処理系もある。 この方法を 演算子順位法(operator precedence parsing) と呼ぶ。

確認問題 8-1

ある言語の公式の文法定義が BNF で公開されている。この文法は左再帰を多く含み、改訂のたびに規則が追加される。 公式の文法定義の形を崩さずに構文解析器を作り、改訂にも追従したい。この条件で最も適した方法はどれか。

  1. 文法定義をパーサー生成系に与え、LR 系の構文解析器を生成する
  2. 文法定義をもとに再帰下降パーサーを手で書く。手で書けるため、改訂にも柔軟に対応できる
  3. LL(1) の構文解析器を作る。LR 系より処理速度が高いため、大きな入力でも有利である
  4. 文法定義の各規則を正規表現に変換し、有限オートマトンで解析する
解答

正解: (A)

LR 系は左再帰をそのまま扱えるため、文法定義の形を崩さずに使える。改訂のたびに文法を差し替えて生成し直せばよく、新しい規則が問題を起こせば競合として報告される。

(B) は、条件のうち「文法定義の形を崩さない」を満たさない。再帰下降法では左再帰を除く書き換えが必要であり、改訂のたびに書き換えと確認をやり直すことになる。 (C) は、処理速度を根拠にした誤りである。LL(1) も LR 系も入力の長さに比例する時間で動き、速度は選択を左右しない。また LL(1) にするには、やはり左再帰を除く書き換えが要る。 (D) は、正規表現と有限オートマトンの限界を見落としている。括弧の入れ子のような構造は、有限個の状態では判定できない。

9再帰下降パーサーの実装

文法 G に減算と除算を加えた次の文法について、構文木を組み立てて返す再帰下降パーサーを作る。 減算と除算は加算・乗算と同じ優先順位で、左結合とする。 

<expr>   ::= <term> { ( "+" | "-" ) <term> }
<term>   ::= <factor> { ( "*" | "/" ) <factor> }
<factor> ::= "(" <expr> ")" | 数

出力する木 — 抽象構文木

構文解析器が後段に渡すのは、図 1-1 のような構文木そのものではなく、計算に必要な構造だけを残した 抽象構文木(abstract syntax tree, AST) である。 <expr> → <term> → <factor> のように一本道で続く節や、括弧は残さない。括弧が表していた結び付きは、木の形として残る。 AST の節は次の二種類とする。

  • 葉(v) — 数 v を表す
  • 節(演算子, 左, 右) — 二つの部分木を演算子で結んだ式を表す

以下では、AST を +(1, *(2, 3)) のように、演算子の後に左右の部分木を括弧で並べて書く。

字句列と基本の操作

字句解析器が出力した字句は、種別（数, "+", "(" など）と、数であればその値、そしてソースコード上の位置（行と列）を持つとする。 位置は、誤りを報告するために欠かせない。

1. もし 次の字句() の種別が k ならば 読み進める()

各関数は、自分の担当する部分を読み終えたら、その部分の AST を返す。 呼び出した側は、返された部分木を材料にして、より大きな木を組む。

式() の 5 行目が、左結合の木を作る箇所である。 ループを一周するたびに、それまでの木 左 を左の子とする新しい節で 左 を置き換えるため、木は左へ伸びる。 8 - 3 - 2 であれば、一周目で -(8, 3)、二周目で -(-(8, 3), 2) となる。

エラー処理

構文エラーの報告には、少なくとも次の三つを含める。

  • 誤りの位置 — 次の字句が持つ行と列
  • 期待していたもの — 期待する() に渡した種別。因子() では 数 または "("、すなわち FIRST(<factor>) である
  • 実際に現れたもの — 次の字句の種別と、元の文字列
手続き 構文エラー(期待したもの)
1. t ← 次の字句()
2. 「t の行:t の列: 期待したもの が必要だが t が現れた」と出力する

上の手続きは、最初の誤りを報告した時点で解析を終える。演習の規模であればこれで足りる。 実用の処理系では、誤りの後に文の区切りや閉じ括弧のような字句まで読み飛ばし、そこから解析を再開して、一度に複数の誤りを報告する。 この回復の方法を パニックモード(panic mode) と呼ぶ。 これが効くのは、一回の翻訳に時間がかかる大きなプログラムで、誤りを一つ直すたびに翻訳し直す手間が大きい場合である。 ただし、読み飛ばしの範囲が不適切だと、本来の誤りに続いて見かけ上の誤りが連鎖的に報告される。

10総括

  • 構文解析器が解く問題 — 字句列から構文木を組むには、各段階で使う規則を決めなければならない。 根から展開するのがトップダウン、葉からまとめるのがボトムアップである。上限のない入れ子を扱うため、どちらも深さに比例する記憶を持つ。
  • 再帰下降法 — 非終端記号ごとに関数を作り、右辺を手順として写し取る。終端記号は照合して読み進め、選択肢は次の字句で決める。
  • 左再帰と繰り返しへの書き換え — 左再帰をそのまま関数にすると、字句を読まずに自分を呼んで止まらない。 繰り返しに書き換え、ループの中で木を左へ伸ばせば、左結合の木が得られる。
  • FIRST と FOLLOW — 選択肢どうしの FIRST が重ならず、ε になりうる選択肢では FOLLOW とも重ならない文法が LL(1) であり、バックトラックなしで解析できる。
  • 再帰下降による解析の追跡 — 呼び出し木は構文木の形をしている。呼び出しは根から始まり、部分木は葉の側から戻りながらまとまる。
  • シフトと還元 — 字句をスタックに積み、頂上が右辺に一致したら左辺にまとめる。還元の順は最右導出の逆であり、左再帰をそのまま扱える。
  • LR 構文解析 — スタックの中身を有限個の状態に要約し、状態と次の字句で表を引いてシフトと還元を選ぶ。表はパーサー生成系が作り、あいまいな文法では競合が報告される。
  • 使い分け — どちらも入力の長さに比例する時間で動く。既存の文法をそのまま使うならボトムアップ、文法を自分で決められ、分かりやすい誤りの報告が要るなら再帰下降法が適する。
  • 再帰下降パーサーの実装 — 各関数が部分木を返し、最後に入力の終わりを確かめる。誤りは位置・期待したもの・実際に現れたものを添えて報告し、木の形と誤った入力の両方で動作を確かめる。

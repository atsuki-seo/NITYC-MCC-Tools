1部品が動いても処理系は動かない

字句解析器・構文解析器・意味解析器は、それぞれ単体で作り、単体で動作を確かめることができる。 しかし、単体で正しく動く部品を三つ並べても、それだけでは一つの言語処理系にならない。 つないだ途端に動かなくなる例は珍しくない。

  • 字句解析器は加算記号の種別を PLUS と名付けたが、構文解析器は ADD を待っている
  • 構文解析器は二項演算の節点に「演算子・左・右」の順で子を持たせたが、評価器は「左・演算子・右」の順で取り出している
  • 意味解析器が誤りを報告しようとしたが、トークンが行番号を持っていないため、どの行の誤りかを示せない

図 1-1 は、上の二つを境界の両側に並べたものである。いずれも各部品の内部には誤りがない。誤りがあるのは、部品と部品の間で受け渡すデータについての取り決めである。 段階ごとの正しさと、段階をつないだ全体の正しさは別の事柄であり、後者は前者から自動的には得られない。

本講では、一つの小さな言語を例に、字句解析から実行までを一続きの処理系として組み上げる手順を扱う。 例とする言語は、整数・真偽値・変数・条件分岐・繰り返し・出力だけを持つ。次はこの言語で書いたプログラムである。 

# 1 から 5 までの和を求める
let i = 1
let sum = 0
while i < 6 do
  sum = sum + i
  i = i + 1
end
print sum

このプログラムを入力すると 15 を出力する処理系を、次の観点から組み立てる。

  • 言語仕様の決め方 — 字句規則・文法・型規則・実行の意味
  • 段階をつなぐデータ — トークン列・抽象構文木・記号表
  • 最小構成から段階的に機能を足す進め方
  • 実行の方式 — 木を辿る評価と命令列の生成
  • テストの仕方と、レポートにまとめる観点
本講の到達点
  • 作ろうとする言語の仕様を、字句規則・文法・型規則・実行の意味に分けて記述できる
  • 各段階の間で受け渡すデータを定め、段階を一続きの処理系としてつなげられる
  • 最小構成から機能を足していく順序を計画し、各段階で手を入れる箇所を特定できる
  • 段階ごとのテストと全体のテストを設計し、設計判断とその理由をレポートにまとめられる
確認問題 1-1

ある処理系の字句解析器と構文解析器を、別々の担当者が作成した。 どちらも各自が用意したテストをすべて通過したが、二つをつないで実行すると、構文解析器が最初のトークンで誤りを報告した。 原因として最も考えられるものはどれか。

  1. 字句解析と構文解析は本来一つの段階であり、別々に作成したこと自体が誤りである
  2. 字句解析器が出力するトークンの種別名や持たせた情報が、構文解析器の想定と食い違っている
  3. 構文解析器のテストに用いた入力が長すぎ、短い入力での動作が確かめられていない
  4. 各部品のテストが通過している以上、原因は処理系の外の実行環境にある
解答

正解: (B)

各担当者は、自分が想定したトークンの形でテストを書いている。字句解析器のテストは字句解析器の想定に、 構文解析器のテストは構文解析器の想定に従うため、両者の想定が食い違っていてもそれぞれのテストは通過する。 食い違いはつないだときに初めて表に出る。

(A) は段階の分離そのものを誤りとしているが、分離は関心を分けるための正当な設計である。 問題は分けたことではなく、分けた部品の間の取り決めを共有しなかったことにある。 (C) は入力の長さを原因としているが、最初のトークンで失敗しているので入力の長さは関係しない。 (D) は単体テストの通過を全体の正しさの証拠とみなす誤りである。単体テストは部品の内部しか確かめない。

2言語仕様を字句・文法・型規則で定める

処理系を書き始める前に、その処理系が受け付ける言語を文書として定める。 この文書を 言語仕様(language specification) と呼ぶ。 仕様がないまま実装を進めると、実装がたまたま示した振る舞いが言語の定義になる。 その振る舞いが正しいのか誤りなのかを判定する拠り所がないため、テストの期待値も書けない。

言語仕様は、コンパイラの処理段階に対応する層に分けて書く。各層は対応する段階の実装の拠り所になる。

表 2-1　言語仕様の層と、それぞれが定める事柄。どの層を決め残しても、 その層に属する振る舞いは実装の都合で決まってしまう。

層記述の手段定める事柄決め残した場合に起こること
字句規則 正規表現 整数・識別子・予約語・演算子の形、読み飛ばす文字 ifx を一つの識別子とみなすか、if と x に切るかが定まらない
文法 EBNF 文と式の形、演算子の優先順位と結合の向き 1 + 2 * 3 や 8 - 3 - 2 に対する構文木が一つに定まらない
型規則 規則の一覧 演算に許される型の組合せ、条件式の型、宣言と代入の整合 if 1 then … を受理するか拒否するかが定まらない
実行の意味 文章・評価手順 各構文を実行したときに起こること、実行時の誤りの扱い 0 による除算で停止するのか、何かの値を返すのかが定まらない

字句規則

トークンの種別ごとに、その字面の形を正規表現で定める。例とする言語の字句規則を表 2-2 に示す。

表 2-2　例とする言語の字句規則と種別名。種別名は字句解析器と構文解析器が共有する取り決めであり、処理系の内部ではこの名前でトークンを区別する。 予約語は識別子と同じ形をしているため、識別子の規則から除く旨を明記しておく。

種別名形
INT[0-9]+（例: 0, 42）
IDENT[a-z][a-z0-9]*、ただし予約語を除く（例: i, sum, x1）
LET IF THEN ELSE WHILE DO END PRINT TRUE FALSE予約語 let if then else while do end print true false。種別名は字面を大文字にしたもの

規則が複数の切り方を許す場合の決め方も仕様に含める。例とする言語では、 できるだけ長い字面を一つのトークンとして切り出す 最長一致(longest match) を採る。 これにより ifx は一つの識別子に、== は二つの = ではなく一つの比較演算子になる。 そのうえで、切り出した字面が予約語と一致すれば予約語の種別を与える。 この二つの手順を、一文字ずつ追うと図 2-1 のようになる。

文法

文と式の形を EBNF で定める。{ } は 0 回以上の繰り返し、[ ] は省略可能な部分を表す。 INT と IDENT は、字句規則で定めた整数と識別子のトークンを指す。 

<program> ::= { <stmt> }
<stmt>    ::= "let" IDENT "=" <expr>
            | IDENT "=" <expr>
            | "print" <expr>
            | "if" <expr> "then" { <stmt> } [ "else" { <stmt> } ] "end"
            | "while" <expr> "do" { <stmt> } "end"
<expr>    ::= <arith> [ ( "<" | "==" ) <arith> ]
<arith>   ::= <term> { ( "+" | "-" ) <term> }
<term>    ::= <factor> { ( "*" | "/" ) <factor> }
<factor>  ::= INT | "true" | "false" | IDENT | "(" <expr> ")"

演算子の優先順位は、規則の階層として文法に組み込まれている。<arith> は <term> を部品とし、 <term> は <factor> を部品とする。このため 2 + 3 * 4 では、 3 * 4 が先に一つの <term> にまとまり、その後で + の右辺になる（図 2-2 の左）。 優先順位を文法の階層で表しておけば、一つの式に対する構文木は一通りに定まる。 階層を設けずに全演算子を一つの規則に並べると、文法は 曖昧(ambiguous) になり、 どの木を選ぶかが構文解析器の書き方次第になる。左から順にまとめる書き方を選べば、図 2-2 の右の木ができる。

文の区切りに記号を用いていないことも、文法から読み取れる。各文は予約語か識別子で始まり、 式は演算子が続かなくなった時点で終わるため、区切り記号がなくとも文の切れ目は一通りに定まる。 構文解析器が受け取るのは改行を含まないトークン列であり、文の切れ目はこの規則だけから決まる（図 2-3）。 区切り記号を設けるかどうかは言語設計者の選択であり、設けない場合はこの性質が成り立つことを確かめておく必要がある。

型規則

例とする言語の型は、整数を表す int と真偽値を表す bool の二つである。 演算と文ごとに、許される型の組合せと結果の型を定める。このような規則の集まりを 型規則(typing rules) と呼ぶ。

表 2-3　例とする言語の型規則。条件の欄を満たさない入力は意味解析で拒否する。 変数の型は宣言時の初期値の型から定まり、以後は変わらない。

構文条件結果
e1 + e2（- * / も同様）e1 と e2 がともに intint
e1 < e2e1 と e2 がともに intbool
e1 == e2e1 と e2 が同じ型bool
変数の参照 xx が宣言済み宣言時に記録した型
let x = ex が未宣言x を e の型で登録する
x = ex が宣言済みで、e の型が x の型と一致—
if e then …、while e do …e が bool—
print ee が int または bool—

型は AST の葉から根に向かって決まる。整数の字面は int、true と false は bool、 変数の参照は記号表に記録された型を持つ。演算の節点の型は、子の型が出揃った時点で表 2-3 の規則から決まる。 規則の条件を満たさない節点が見つかれば、そこで拒否する。図 2-4 は、例のプログラムに現れる二つの式と、拒否される式について、各節点に型を書き添えたものである。 このように各節点に型を書き添えた AST を、型の注釈つき AST(type-annotated AST) と呼ぶ。

実行の意味

最後に、各構文を実行したときに何が起こるかを文章で定める。例とする言語では次のように定める。

  • 二項演算は左の式、右の式の順に評価し、その後で演算を行う
  • / は整数の除算とし、商の小数部を切り捨てる。右辺が 0 であれば実行時の誤りとして実行を停止する
  • while は条件を評価し、真である間、本体の文を上から順に実行する
  • 変数の有効範囲はプログラム全体で一つとする。if や while の本体で宣言した変数も、その外から参照できる

最後の項目は、ブロックごとに有効範囲を設ける言語も多いなかで、あえて単純な側を選んだものである。 このように、仕様は「何を選ばなかったか」も含めて明記する。 書かれていない事柄は、実装した人の判断が暗黙に仕様になる。

確認問題 2-1

ある処理系に print 1 + 2 * 3 を入力したところ、9 が出力された。 字句解析器はトークンを正しく切り出しており、乗算そのものの計算にも誤りはなかった。 この誤りの原因となった仕様上の不備として、最も適切なものはどれか。

  1. 字句規則で、* の規則が + の規則より後に書かれていた
  2. 文法で、+ と * が同じ階層の規則に並べられ、左から順に結合されていた
  3. 型規則で、* の結果の型が定められていなかった
  4. 実行の意味で、二項演算の左右の評価順序が定められていなかった
解答

正解: (B)

出力の 9 は (1 + 2) * 3 の値である。+ と * が同じ階層にあると、 左から順に結合して 1 + 2 が先にまとまる。乗算を一段深い規則に置けば、 2 * 3 が先にまとまり、構文木の形として優先順位が固定される。

(A) の字句規則の記述順は、トークンの切り出し方に関わることはあっても、演算の優先順位は決めない。 問題文でもトークンは正しく切り出されている。 (C) の型規則は演算が許されるかを定めるもので、どちらの演算を先に行うかとは関係がない。 (D) の評価順序は左右の部分式のどちらを先に計算するかであり、木の形が同じなら結果は変わらない。 この式の左右の部分式はどちらも副作用を持たないため、評価順序を変えても 9 と 7 の違いは生じない。

3段階をつなぐデータ — トークン列・AST・記号表

段階と段階の間で受け渡すデータの取り決めを、その段階間の インタフェース(interface) と呼ぶ。 § 1 で挙げた失敗は、いずれもこのインタフェースを文書にしないまま部品を作ったことに由来する。 言語仕様と同じく、インタフェースも実装の前に決めて書き出しておく。

トークン — 種別・字面・位置

字句解析器と構文解析器の間のインタフェースはトークン列である。一つのトークンには次の三つを持たせる。

  • 種別 — 整数・識別子・let・+ などの区別。構文解析器はこれだけを見て文法の規則を選ぶ
  • 字面 — 切り出した文字列そのもの。識別子の名前や整数の値として、後段で用いる
  • 位置 — ソースコード上の行と列。後段が誤りを報告するとき、どこの誤りかを示すために用いる

種別の名前は、表 2-2 の字句規則と一対一に対応させて一覧にしておく。 位置は字句解析器でしか記録できない。空白や改行は字句解析の段階で捨てられるため、後段では位置を復元できないからである。 図 3-2 は、例のプログラムの 5 行目を三つの情報を持つトークンの列にしたものである。位置は「行:列」の形で記録する。

AST — 構造だけを残す

構文解析器と、意味解析器・評価器の間のインタフェースは 抽象構文木(abstract syntax tree, AST) である。 AST の節点の種類は、文法の構文ごとに一つずつ定める。例とする言語では次の節点を置く。

  • 式の節点 — 整数、真偽値、変数の参照、二項演算（演算子・左の子・右の子）
  • 文の節点 — let（名前・式）、代入（名前・式）、print（式）、if（条件・真の場合の文の列・偽の場合の文の列）、while（条件・本体の文の列）

各節点が持つ子の名前と順序まで書き出しておけば、評価器を書く側は構文解析器の内部を読まずに済む。 また、各節点にも元のトークンの位置を写しておく。意味解析は AST だけを見て誤りを報告するためである。 図 3-3 は、例のプログラム全体をこれらの節点で表したものである。

式の部分では、ソースコードにあった括弧が AST から消える。図 3-4 は括弧を含む文の例である。

記号表と環境 — 解析時の表と実行時の表

意味解析器は、宣言された名前とその型を 記号表(symbol table) に登録する。 let の節点に出会えば登録し、変数の参照に出会えば記号表を引いて型を得る。 未宣言の名前の参照や、同じ名前の二重宣言は、この表を引いた時点で検出できる。

これに対し、評価器が実行中に名前と現在の値を結び付けておく表を 環境(environment) と呼ぶ。 どちらも名前を鍵とする表であるが、記号表はプログラムを実行する前に一度だけ作られ、型を記録する。 環境は実行の進行に伴って書き換えられ、値を記録する。 例のプログラムでは、記号表の i は最初から最後まで int であるが、環境の i は 1 から 6 まで変化する（図 3-5）。

確認問題 3-1

トークンに、ソースコード上の行と列を持たせておく主な理由として、最も適切なものはどれか。

  1. 構文解析器が、トークンの並び順を行と列から復元するため
  2. 構文解析器や意味解析器が誤りを報告するとき、ソースコード上の箇所を示すため
  3. 同じ字面の識別子が異なる変数を表すとき、それらを区別するため
  4. 評価器が、行の順にプログラムを実行するため
解答

正解: (B)

空白や改行は字句解析の段階で捨てられるため、後段の段階は自分でソースコード上の位置を求められない。 誤りを検出するのは後段であっても、その位置を記録できるのは字句解析器だけである。

(A) の並び順は、トークン列が列である以上、位置を見なくとも保たれている。 (C) は名前の区別と位置を混同している。同じ名前が別の変数を指すかどうかは有効範囲の規則で決まり、 記号表がそれを扱う。 (D) は実行の順序を位置で決めるとみなす誤りである。実行の順序は AST の構造と実行の意味で定まる。 while の本体は行の順を遡って繰り返し実行される。

確認問題 3-2

通常の算術の優先順位に従って、次の式の AST を作る。括弧は節点として保持しない。 演算子の節点と葉の節点を合わせた節点の総数はいくつか。 

(a + b) * c - d * e
  1. 4
  2. 5
  3. 9
  4. 11
解答

正解: (C)

根は優先順位の最も低い - である。その左の子は * で、 この * の左の子が +（子は a と b）、右の子が c である。 - の右の子はもう一つの *（子は d と e）である。 演算子の節点が 4 個、葉が 5 個で、合計 9 個になる。

(A) は演算子の節点だけを、(B) は葉だけを数えている。 (D) は丸括弧の二つのトークンを節点として数えた結果である。括弧の役目は + を * の子に置くという木の形に移っており、 節点としては残らない。

4最小構成から機能を縦に足す

言語仕様は全体を先に決めるが、実装は全体を一度に書かない。 まず、ごく小さな言語について字句解析から実行までの全段階を通しで動かし、そこに機能を一つずつ加えていく。 最初に作る、全段階を貫いて動く最小の処理系を ウォーキングスケルトン(walking skeleton) と呼ぶ。 例とする言語では、print 42 のように整数を一つ出力するだけの処理系がこれにあたる。 図 4-1 の上段がその処理系のデータの流れであり、下段はそこに加算を足したときの差分である。

表 4-1　機能を加える順序と、各段階で加える内容。どの機能も字句解析から実行までの全段階に手を入れる。 各行を終えた時点で、そこまでの機能を持つ処理系が通しで動く。

加える機能字句解析構文解析意味解析実行
整数一つの出力 整数、print "print" INT 検査なし（素通し） 値を出力する
四則演算と括弧 + - * / ( ) <arith> <term> <factor> 検査なし（型が int だけのため） 二項演算の評価、0 による除算の停止
変数 識別子、let、= let 文、代入文、変数の参照 記号表の導入、未宣言・二重宣言の検出 環境の導入

横に作るか、縦に作るか

これに対し、字句解析器を全機能について完成させてから構文解析器に移る、という進め方もある。 表 4-1 の列ごとに埋める進め方であり、ここでは「横に作る」と呼ぶ。行ごとに埋める進め方は「縦に作る」と呼ぶ。 両者の違いは、作業の総量ではなく、処理系が初めて通しで動く時点に現れる（図 4-2）。

縦に作る進め方には次の利点がある。

  • インタフェースの食い違いが、関わる構文が少ないうちに見つかる。整数一つの段階で見つかった食い違いは、トークンの種別が一つしかないため直す範囲も小さい
  • どの時点で作業を止めても、そこまでの機能で動く処理系が残る。提出期限が決まっている作業では、この性質が、期限の時点で何も動かないという事態を防ぐ
  • 機能を一つ加えて動かなくなれば、原因はその機能の追加分にほぼ限られる

代償として、後から加える機能のために既存の部分を書き直すことがある。たとえば比較を加えるときには、 <arith> の上に <expr> の階層を一段増やす必要がある。 変数までが動く時点の文法は次のとおりである。 

<stmt>    ::= "let" IDENT "=" <arith> | IDENT "=" <arith> | "print" <arith>
<arith>   ::= <term> { ( "+" | "-" ) <term> }
<term>    ::= <factor> { ( "*" | "/" ) <factor> }
<factor>  ::= INT | IDENT | "(" <arith> ")"

比較と真偽値を加えた後の文法は次のようになる。強調した一行が増えた規則である。 

<stmt>    ::= "let" IDENT "=" <expr> | IDENT "=" <expr> | "print" <expr>
<expr>    ::= <arith> [ ( "<" | "==" ) <arith> ]
<arith>   ::= <term> { ( "+" | "-" ) <term> }
<term>    ::= <factor> { ( "*" | "/" ) <factor> }
<factor>  ::= INT | "true" | "false" | IDENT | "(" <expr> ")"

規則が一行増えたほかは、<arith> を参照していた箇所が <expr> に置き換わり、 <factor> に true と false が加わっただけである。 <arith> と <term> の規則には手が入らない。 この書き直しが小さく済むかどうかは、言語仕様を最初に全体まで決めてあるかで決まる。 文法の階層が仕様として先にあれば、実装はそれを上から順に埋めていくだけになる。 仕様は全体を先に決め、実装は縦に足すという組合せが、横に作る進め方と縦に作る進め方の利点を両立させる。

横に作る進め方が適するのは、言語仕様とインタフェースが最初から確定しており、各段階の出力を単体のテストで十分に確かめられる場合である。 複数の人が段階ごとに分担する場合にも採られるが、その場合はインタフェースの文書が唯一の頼りになる。

演算子を加えるときの注意 — 左再帰

四則演算を加える段階で、引き算を次のように書きたくなる。 

<arith> ::= <arith> "-" <term> | <term>

規則の右辺の先頭に左辺と同じ記号が現れることを 左再帰(left recursion) と呼ぶ。 再帰下降法でこの規則をそのまま関数にすると、算術式を解析する関数がトークンを一つも読み進めないまま自分自身を呼び出し、 終わらない再帰に陥る（図 4-4 の右）。

終わらない再帰を避けるだけなら、右辺の並びを入れ替えて <arith> ::= <term> "-" <arith> | <term> と書く方法もある。 右辺の末尾に左辺と同じ記号が現れるこの形を 右再帰(right recursion) と呼ぶ。 右再帰では関数が先に項を一つ読むため再帰は終わるが、木の形が変わり、引き算の値が仕様と食い違う（図 4-4 の左）。

再帰下降法で書くときは、§ 2 の文法のように繰り返しの形に書き換え、次の手順で木を作る。 

算術式を解析する():
1. 左 ← 項を解析する()
2. 次のトークンが + または - である間、繰り返す
   2.1 演算子 ← そのトークンを読み進める
   2.2 右 ← 項を解析する()
   2.3 左 ← 二項演算の節点(演算子, 左, 右)
3. 左 を返す

手順 2.3 で、それまでに作った木を新しい節点の左の子に置く。このため、繰り返しのたびに木は左下へ伸びていく（図 4-3）。 同じ優先順位の演算子を左から順にまとめるこの性質を 左結合(left associativity) と呼ぶ。

誤りやすい点

右再帰への書き換えは終わらない再帰を止めるが、結合の向きを変える。足し算と掛け算は結合の向きで値が変わらないため、 この誤りは引き算か割り算を二つ以上並べた式でなければ表に出ない。テストにはそうした式を含めておく。

確認問題 4-1

四則演算までが通しで動く処理系に、変数（let による宣言、参照、代入）を加える。 手を入れる必要がある段階の組合せとして、最も適切なものはどれか。

  1. 字句解析と構文解析だけ
  2. 意味解析と実行だけ
  3. 実行だけ
  4. 字句解析・構文解析・意味解析・実行のすべて
解答

正解: (D)

字句解析には識別子・let・= のトークンを、構文解析には let 文・代入文・変数の参照の規則を加える。 意味解析では記号表を導入して未宣言・二重宣言を検出し、実行では環境を導入して値を記録する。 新しい構文を伴う機能は、一般に全段階に及ぶ。

(A) は変数を形だけの問題とみなしている。名前が宣言済みかどうかは形からは判定できない。 (B) は変数を意味だけの問題とみなしている。識別子や let のトークンがなければ、そもそも変数を含む文を読めない。 (C) は環境に値を記録すれば足りると考えているが、それでは読み込みも検査もできない。

確認問題 4-2

規則 <arith> ::= <arith> "-" <term> | <term> を再帰下降法で実装するために書き換える。 8 - 3 - 2 の値が 3 になるものはどれか。

  1. <arith> ::= <term> "-" <arith> | <term> と書き換え、規則どおりに関数を作る
  2. <arith> ::= <term> { "-" <term> } と書き換え、項を読むたびに、それまでの木を左の子とする節点を作る
  3. 書き換えずにそのまま関数にする。再帰下降法は左再帰を自動的に処理できる
  4. <arith> ::= <term> { "-" <term> } と書き換え、すべての項を読み終えてから、右端の二つから順にまとめる
解答

正解: (B)

繰り返しの形にすれば、関数は必ず項を一つ読んでから次へ進むため、終わらない再帰は起こらない。 さらに、それまでの木を左の子に置けば、(8 - 3) - 2 = 3 の形の木ができる。

(A) は左再帰を右再帰に置き換えたもので、終わらない再帰は解消するが、木は 8 - (3 - 2) の形になり値は 7 になる。 (D) も右端からまとめるため同じく 7 になる。いずれも結合の向きを取り違えている。 (C) は誤りで、再帰下降法は左再帰をそのままでは扱えない。関数が入力を読み進めないまま自分自身を呼び出し続ける。

5実行の方式 — 木を辿る評価と命令列の生成

意味解析を通過した AST を実行する方式には、AST をそのまま辿って実行する方式と、 AST から別の機械向けの命令列を生成してそれを実行する方式がある。

木を辿る評価

AST の節点の種類ごとに評価の手順を書き、子の節点について同じ手順を再帰的に呼び出す。 この方式の処理系を 木構造インタプリタ(tree-walking interpreter) と呼ぶ。 式の評価と文の実行は、それぞれ次のように書ける。 

評価する(節点, 環境):
1. 節点が整数または真偽値ならば、その値を返す
2. 節点が変数の参照ならば、環境からその名前の値を取り出して返す
3. 節点が二項演算ならば
   3.1 左 ← 評価する(左の子, 環境)
   3.2 右 ← 評価する(右の子, 環境)
   3.3 演算子が / で 右 = 0 ならば、実行時の誤りとして停止する
   3.4 演算子に応じて 左 と 右 から計算した値を返す

実行する(文, 環境):
1. let 文または代入文ならば、環境[名前] ← 評価する(式, 環境)
2. print 文ならば、評価する(式, 環境) の値を出力する
3. if 文ならば、評価する(条件, 環境) が真なら真の場合の文の列を、偽なら偽の場合の文の列を順に実行する
4. while 文ならば、評価する(条件, 環境) が真である間、本体の文の列を順に実行する

この手順は、§ 2 で文章として定めた実行の意味をほぼそのまま書き写したものになっている。 手順 3.1 と 3.2 の順序は「左の式、右の式の順に評価する」という仕様に、手順 3.3 は 0 による除算の扱いに対応する。 意味解析を通過した AST だけを受け取るため、評価器の中で型を調べ直す必要はない。

図 5-1 は、環境が i = 2、sum = 1 のとき、すなわち while の 1 回目を終えた時点（図 3-5 の「1 回目の後」）で、 5 行目の右辺 sum + i を評価する様子である。二項演算の節点の手順が左右の子について自分を呼び出し、子は環境から値を取り出して返す。 返ってきた二つの値から 3 が計算され、代入文の手順が環境の sum を 3 に書き換える。 続く 6 行目で i が 3 になり、環境は図 3-5 の「2 回目の後」の (3, 3) に至る。

スタック機械向けの命令列の生成

もう一つの方式は、AST を命令の列に変換し、その命令列を実行する方式である。 簡単な変換先として、値を積み上げる表を一つだけ持ち、命令がその表の上端を操作する スタック機械(stack machine) がある。 例とする言語の式に対しては、次の命令があれば足りる。

  • PUSH n — 値 n を積む。LOAD x — 変数 x の値を積む。STORE x — 一つ取り出して変数 x に記録する
  • ADD SUB MUL DIV LT EQ — 二つ取り出して演算し、結果を積む。SUB と DIV は、下にあった値から上にあった値を引く・割る
  • PRINT — 一つ取り出して出力する

二項演算の節点は、左の子の命令列、右の子の命令列、自分の演算命令、の順に命令を出力すればよい。 子をすべて訪れてから親を訪れるこの順序を 後行順(post-order) と呼ぶ。 演算命令が実行される時点で、二つの被演算子の値はスタックの上端に揃っている（図 5-2）。

被演算子を積む順序は、引き算と割り算では結果を左右する。10 - 4 では、左の子 10 を先に、右の子 4 を後に積み、 SUB は下にあった 10 から上にあった 4 を引く。 

PUSH 10      スタック: 10
PUSH 4       スタック: 10 4
SUB          スタック: 6

左右の子の命令列を逆の順に出力すると、スタックは 4 10 となり、SUB は 4 - 10 = -6 を計算する。 足し算と掛け算では順序を誤っても値が変わらないため、この誤りは引き算か割り算を含むテストでなければ見つからない。

文の命令列も同じ考え方で作れる。代入文は右辺の命令列の後に STORE を、print 文は式の命令列の後に PRINT を置く。 while 文と if 文には、命令列の中の位置を表す名札と、そこへ移る命令を用いる。 JUMP L は名札 L へ移り、JUMP_IF_FALSE L は一つ取り出した値が偽なら名札 L へ移る。 while 文は次の形になる。 

L1: 条件式の命令列
    JUMP_IF_FALSE L2
    本体の文の列の命令列
    JUMP L1
L2: （while 文の次の文の命令列）

if 文は次の形になる。真の場合の文の列を実行し終えたら、JUMP L2 で偽の場合の命令列を飛び越す。 この JUMP を置き忘れると、条件が真のときにも偽の場合の文が続けて実行される。 

    条件式の命令列
    JUMP_IF_FALSE L1
    真の場合の文の列の命令列
    JUMP L2
L1: 偽の場合の文の列の命令列
L2: （if 文の次の文の命令列）

これらを組み合わせると、例のプログラム全体の命令列は次のようになる。右側は対応するソースコードの行である。 

    PUSH 1               let i = 1
    STORE i
    PUSH 0               let sum = 0
    STORE sum
L1: LOAD i               while i < 6 do
    PUSH 6
    LT
    JUMP_IF_FALSE L2
    LOAD sum               sum = sum + i
    LOAD i
    ADD
    STORE sum
    LOAD i                 i = i + 1
    PUSH 1
    ADD
    STORE i
    JUMP L1              end
L2: LOAD sum             print sum
    PRINT

図 5-3 は、この命令列を 1 回目の繰り返しと、繰り返しを抜ける最後の回について、1 命令ずつ辿ったものである。 1 回目の終わりの (i, sum) = (2, 1) は、評価器で実行したときの図 3-5 の「1 回目の後」と一致する。

木を辿る評価と命令列の生成の使い分け

表 5-1　木を辿る評価と命令列の生成の比較。小さな言語で問題になりやすいのは上の三行であり、 実行速度の差が選択を左右するのは、繰り返しの多いプログラムを実際に走らせる場合に限られる。

観点木を辿る評価命令列の生成
実装の量 節点の種類ごとに評価の手順を書くだけでよい 命令の定義、命令列の生成器、命令を実行する仕組みの三つが要る
仕様との対応 評価の手順がそのまま実行の意味の記述になる 実行の意味が、生成の規則と命令の定義の二か所に分かれる
誤りの追いやすさ 誤った値は、それを計算した節点の手順に直接たどれる 生成の誤りか、命令の実行の誤りかを切り分ける必要がある

独自の言語を初めて作るときは、まず木を辿る評価で処理系を完成させ、言語の意味を確定させる。 命令列の生成に取り組むのはその後である。こうしておくと、評価器の出力を命令列の実行結果の正解として使える。 同じプログラムを二つの方式で実行して出力を比べ、食い違いがあれば生成側の誤りを疑えばよい。 このように、同じ入力を二つの実装に与えて結果を比べる確認の仕方を 差分テスト(differential testing) と呼ぶ。

確認問題 5-1

式 (4 - 1) * 2 の AST を後行順に辿り、図 5-2 と同じ命令を用いて命令列を生成した。 正しい命令列はどれか。SUB は、下にあった値から上にあった値を引く。

  1. PUSH 4, PUSH 1, SUB, PUSH 2, MUL
  2. PUSH 4, SUB, PUSH 1, MUL, PUSH 2
  3. MUL, SUB, PUSH 4, PUSH 1, PUSH 2
  4. PUSH 1, PUSH 4, SUB, PUSH 2, MUL
解答

正解: (A)

根は * で、左の子が -（子は 4 と 1）、右の子が 2 である。 後行順では 4、1、-、2、* の順に訪れる。 実行するとスタックは 4 → 4 1 → 3 → 3 2 → 6 と変化し、正しく 6 が得られる。

(B) はソースコード上の記号の並び（中置の順）のまま命令を並べたもので、SUB の時点で値が一つしか積まれていない。 (C) は親を先に訪れる順序（前行順）で並べたもので、演算命令が被演算子より先に実行される。 (D) は左右の子の順序を逆にしたもので、SUB が 1 - 4 を計算し、結果は -6 になる。

6テスト — 段階ごとの確認と全体の確認

処理系のテストは、段階ごとの確認と、処理系全体の確認の二層で行う。 段階ごとのテストは誤りの箇所を絞り込むために、全体のテストはインタフェースの食い違いを検出するために必要であり、 一方で他方を置き換えることはできない。 ソースコードを入力して最終的な出力を確かめるテストを エンドツーエンドテスト(end-to-end test) と呼ぶ。

表 6-1　テストの単位と、入力・期待する出力の組。期待する出力は、どれも言語仕様から手で求められる形にしておく。

単位入力期待する出力例
字句解析 ソースコード トークン列（種別と字面） ifx == 1 → IDENT(ifx) EQ INT(1)
構文解析 ソースコード AST を文字列に書き出したもの 8 - 3 - 2 → (- (- 8 3) 2)
意味解析 ソースコード 受理、または誤りの種類と位置 print y（y は未宣言）→ 1 行目で未宣言の名前
全体 ソースコード 実行時の出力 § 1 のプログラム → 15

構文解析のテストでは、AST を決まった形式の文字列に書き出す関数を用意しておくと、期待値との比較が文字列の比較で済む。 表 6-1 の例は、節点ごとに「演算子 左の子 右の子」を括弧で囲んで書き出す形式である。 この形式では木の形が括弧の入れ子として表れるため、結合の向きの誤りも一目で分かる。

拒否すべきプログラムをテストする

正しいプログラムを正しく実行できることと同じく、誤ったプログラムを正しく拒否できることも処理系の仕様の一部である。 言語仕様の各規則について、受理すべき例と拒否すべき例の両方を用意する。 拒否すべき例には、どの段階で拒否されるべきかも期待値として書いておく。 後の段階で拒否されたなら、前の段階が受理すべきでない入力を通したことになる。

表 6-2　誤りを含むプログラムと、それを拒否すべき段階。拒否する段階は、その誤りを判定するのに必要な情報が初めて揃う段階である。

プログラム拒否すべき段階根拠となる規則
let x = 3 @ 4字句解析@ に一致するトークンの規則がない
let = 5構文解析let の後には識別子が要る
print y（y は未宣言）意味解析参照する変数は宣言済みでなければならない
let b = 1 < 2 の後に b = 3意味解析代入する値の型が変数の型と一致しない
print 10 / (3 - 3)実行右辺が 0 であることは、値を計算して初めて分かる

機能を足すたびに全テストを流す

縦に作る進め方では、機能を一つ加えるたびに既存の部分に手が入る。 比較を加えるために文法の階層を一段増やせば、四則演算の解析が壊れているかもしれない。 そこで、機能を加えるたびに、それ以前に用意したテストをすべて実行し直す。 以前に通っていたテストが通らなくなっていないかを確かめるこのテストを 回帰テスト(regression test) と呼ぶ。 テストの実行を一つの命令で行えるようにしておくと、確認の手間が機能の数に比例して増えることを避けられる。

たとえば、テストごとにソースコードと期待する出力の組をファイルとして置く。次は § 1 のプログラムの組である。 

tests/sum.src
# 1 から 5 までの和を求める
let i = 1
let sum = 0
while i < 6 do
  sum = sum + i
  i = i + 1
end
print sum

tests/sum.expected
15

全件を実行する命令は、各組について処理系の出力と期待値を比べ、結果を一覧にする。 次は、比較を加えたときに算術式の解析を書き直し、結合の向きを誤った場合の出力の例である。 

sum           通過
precedence    通過
assoc         失敗   期待 4 ／ 実際 6   （9 - 4 - 1）
undeclared    通過
reject_type   通過
---
5 件中 4 件通過、1 件失敗

比較の機能そのもののテストを書いただけでは、この誤りは見つからない。以前の機能のテストを流し直して初めて、壊れたことが分かる。

誤りやすい点

処理系が出力した結果を、そのまま期待値として写してはならない。処理系に誤りがあれば、その誤りが正解としてテストに固定される。 期待値は言語仕様から手で求める。手で求められないほど大きなプログラムは、テストとしても大きすぎる。

確認問題 6-1

例とする言語の仕様に従う処理系に、次のプログラムを入力した。このプログラムを拒否すべき段階はどれか。 

if 1 then
  print 2
end
  1. 字句解析
  2. 構文解析
  3. 意味解析
  4. 実行
解答

正解: (C)

表 2-3 の型規則は、if の条件式が bool であることを求めている。 条件式 1 の型は int であり、このことは実行する前に AST と型規則だけから判定できる。 なお、整数の 0 以外を真とみなす言語もある。その場合このプログラムは受理されるが、それは型規則という仕様の違いであり、 どちらを採るかは言語仕様に明記しておく。

(A) は誤りで、if・1・then などはすべて字句規則に従うトークンである。 (B) も誤りで、文法は "if" <expr> "then" の形しか定めておらず、1 は <expr> として正しい。 (D) は、判定に必要な情報が実行前に揃っているのに実行まで持ち越している。 実行時に検出する方式では、条件式に到達しない限り誤りが見つからない。

7レポートにまとめる観点

作成した処理系のレポートは、読み手が処理系を動かさずに、言語の仕様と処理系の構造、およびその正しさの根拠を把握できるように書く。 動作したという事実だけでは、何をどこまで作ったのか、なぜその設計にしたのかが伝わらない。

表 7-1　レポートにまとめる観点と、それぞれの裏付けとなる資料。各観点は本講で扱った作業の順序に対応しており、 作業の過程で作った文書がそのままレポートの材料になる。

観点書く内容裏付けとなる資料
言語仕様 字句規則、文法、型規則、実行の意味。その言語で書いたプログラムの例 正規表現の一覧、EBNF、型規則の表
処理系の設計 段階の構成と、段階の間で受け渡すデータの定義 トークンの種別の一覧、AST の節点の一覧、記号表と環境の構成
実装の経過 機能を加えた順序と、各機能で各段階に加えた内容 表 4-1 のような計画表と、実際の作業の記録
テスト 受理すべきプログラムと拒否すべきプログラム、期待値と実行結果 テストの一覧と、全テストを実行した結果
考察 設計判断の理由と選ばなかった案、その判断が成り立つ条件。未対応の機能と、対応するには何を変える必要があるか 仕様と設計の各項目

考察で書くのは、感想や作業の苦労ではなく設計判断である。 ある設計を選んだ理由は、選ばなかった案と並べて初めて説明できる。 たとえば有効範囲をプログラム全体で一つにした判断であれば、それによって記号表が単純な表一つで済んだこと、 その代わりに while の本体で宣言した変数が外から見えてしまうこと、 ブロックごとに有効範囲を設けるには記号表を入れ子にする必要があることを書く。 限界を述べることは減点の理由ではなく、仕様と実装を正確に把握していることの証拠である。

確認問題 7-1

作成した処理系のレポートの考察として、最も適切な記述はどれか。

  1. 字句解析器・構文解析器・意味解析器・評価器を実装し、用意したテストはすべて通過した。
  2. 構文解析には再帰下降法を用いた。再帰下降法は、非終端記号ごとに関数を作って解析する手法である。
  3. 優先順位を文法の階層で表していたため、比較演算子は階層を一段加えるだけで追加できた。一方、有効範囲を一つにしたため、while の本体で宣言した変数が外から参照できる。これを防ぐには記号表を入れ子にする必要がある。
  4. 処理系の作成は難しかったが、最後にプログラムが動いたときは達成感があった。
解答

正解: (C)

(C) は、二つの設計判断について、それが何をもたらしたかを利点と限界の両面から述べ、限界を解消する方法まで示している。 読み手はこの記述から、仕様と実装の関係を把握できる。

(A) は結果の報告であり、テストの章に書くべき内容である。なぜその結果になったのか、その設計で何が言えるのかを述べていない。 (B) は手法の一般的な説明であり、自分の処理系についての判断を含んでいない。他の手法ではなくそれを選んだ理由が書かれていない。 (D) は感想であり、処理系の設計について何も述べていない。

8総括

  • 部品が動いても処理系は動かない — 段階ごとの正しさと全体の正しさは別であり、食い違いは段階の間の取り決めに生じる
  • 言語仕様 — 字句規則・文法・型規則・実行の意味の層に分けて実装の前に定める。優先順位は文法の階層で表し、選ばなかった事柄も明記する
  • 段階をつなぐデータ — トークンは種別・字面・位置を持ち、AST は括弧を持たずに構造を木の形で表す。記号表は解析時に名前と型を、環境は実行時に名前と値を結び付ける
  • 縦に足す — 全段階を貫く最小の処理系から始め、機能を一つずつ全段階に加える。仕様は全体を先に決め、実装は縦に足す。左再帰は繰り返しに書き換え、左結合を保つ
  • 実行の方式 — 木を辿る評価は仕様と直接対応し、命令列の生成は後行順の走査で得られる。評価器を先に完成させれば、その出力を生成側の正解として使える
  • テスト — 段階ごとのテストと全体のテストを併用し、拒否すべきプログラムは拒否すべき段階とともに用意する。機能を足すたびに回帰テストを行い、期待値は仕様から手で求める
  • レポート — 仕様・設計・経過・テスト・考察をまとめ、考察では設計判断を選ばなかった案と限界とともに述べる
